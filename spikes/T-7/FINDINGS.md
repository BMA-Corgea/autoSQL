# T-7 · Findings — which write path skips the schema type check?

Stage: `sp-investigate` · Run: **2026-09-01** · Bar: `spikes/T-7/FRAMING.md`

**READ-ONLY.** Two GIMS checkouts read, never written. Every database opened
`mode=ro&immutable=1`. `git log`/`git show` used against `GIMS-Project` — reads, no checkout.

---

## The answer

> **The specific path cannot be attributed, and it does not need to be. Six of GIMS's seven
> `put_record` write paths do no schema validation at all** — so a declared field type is **not**
> a guarantee about stored content, and that is true regardless of which of the six wrote these
> particular rows.
>
> This is FRAMING outcome **(b)**, which the bar accepts, plus the answer that actually matters.

**And the two that validate really do block** — this was checked rather than assumed, because a
validation whose result is discarded is worse than none:

```python
errs += validate_item_against_schema(payload, noun_type, schema, pp, project=project)
if errs:
    return {"ok": False, "errors": errs}        # routes_write.py:75-77, before the write
```

`routes_bulk.py:127-131` does the same, per row, skipping the row rather than the batch.

## 2. The hypothesis that was wrong, and how it was killed

**Hypothesis:** the rows were written while `Glove.size` was a `string`, and the schema was
retyped to `float` later. GIMS lets you edit noun types in the workbench, so this was the obvious
explanation — and it would have been a *much* worse finding, because it would mean any field's
declared type can be falsified retroactively.

**Disproven from git.** `projects/LIMS-System/noun_types.json`, every commit that touched it:

| date | `Glove.size` type |
|---|---|
| 2025-05-29 | field absent |
| **2025-05-30** | **`float`** |
| … every commit since … | `float` |
| 2026-07-03 | `float` |

The rows carry `material` values of **2025-08-12 to 2025-08-27**. The field had been `float` for
**three months** before they were written. **The schema did not move; the write did not check.**

## 3. Why the specific path cannot be named

Three sources of provenance were looked for. None exists:

1. **The rows themselves carry none** — no author, no timestamp, no origin field. The `material`
   field happens to hold a date, but that is a *user-entered value in a mistyped field*, not a
   write timestamp.
2. **`LIMS-System_verb_log` does not cover this.** It records **verbs** (test runs), not noun
   writes, and its earliest row is **2025-10-22** — two months after these rows.
3. **The `GLOV-…` primary keys are autogenerated**, which narrows nothing: `_generate_primary` is
   reachable from validating and non-validating paths alike.

**So the honest answer is that it is not attributable**, and the framing anticipated exactly this.
Naming one of the six on a guess would have been the one outcome the bar refused.

## 5. What it means for autoSQL — the only part that changes a design

**A declared field type is not a guarantee about stored content.** Any autoSQL design that treats
`noun_types.json` as authoritative about what is *in* a column inherits an assumption that six of
seven write paths do not maintain.

**The concrete casualty is T-1 `f3` §3.6, hazard H3** — per-path expression indexes typed by the
declared type:

```sql
CREATE INDEX ... ON instances (((data->>'size')::float8))
```

On this table that statement **fails**, with `invalid input syntax for type double precision`, on
nine real rows. T-1 §D.6.2 had already found the same hazard with a *different* real witness
(`$.payload.blocked_since`, a number on 315 rows and an ISO date on 9). **Two independent
witnesses, in two collections, from two mechanisms.** The hazard is not an edge case.

**The design consequence:** an expression index must either be built with a guard
(`WHERE jsonb_typeof(...) = 'number'`, a partial index), or its build must be expected to fail and
handled — never assumed to succeed because the schema says `float`.

## 6. What this run does NOT establish

1. **Which of the six wrote these rows** (§3) — and no evidence that could settle it exists today.
2. **Whether the unvalidated paths are user-facing.** `grid.py` and `camera.py` are API routes, so
   probably yes, but this run did not trace their auth or exposure. If it matters, that is a GIMS
   security question and its own ticket — **not** something to fix quietly here.
3. **Whether other collections carry the same shape.** Only `Glove` was examined in depth; T-1
   §D.6.2/§D.6.3 found related shapes elsewhere but nobody has swept for type-vs-content mismatch
   systematically.
4. **Nothing about the Postgres path.** This is the SQLite tenant project.
