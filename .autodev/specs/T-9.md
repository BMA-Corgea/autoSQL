# T-9 — Enforce `extra_float_digits = 1`

**Spawned by:** T-6 · **Authority:** GA-13 (*"keep going with T-9"*) · **Pipeline:** `feature@v1` ·
**Lean OFF, risk HIGH**

## 1. The problem, measured

T-6 passed **only** at `extra_float_digits = 1`. At the other two settings the same batteries
produce **62 and 66 wrong numbers** — Postgres printing fewer digits than a double carries. T-6's
fix 2.1 called `efd ≠ 1` a *configuration defect rather than a compiler defect*, and that is only an
honest distinction **if the configuration is actually guaranteed**.

**It is not.** Measured on the demo's own database, 2026-09-01:

| expression | efd 1 | efd 0 | efd −3 |
|---|---|---|---|
| `to_jsonb(1787169706037.0::float8)` | `1787169706037` | `1787169706037` | **`1787169706040`** |
| `to_jsonb(xpr.num('"1787169706037"'))` | `1787169706037` | `1787169706037` | **`1787169706040`** |
| `to_jsonb(1.0::float8/3.0)` | 16 digits | 15 digits | **12 digits** |

That last row is M3's exact witness. **Every path moves.** `extra_float_digits` is a session GUC any
connection can change, and nothing in the runtime notices.

## 2. The finding that shapes the fix

**A function that returns `jsonb` and carries its own `SET extra_float_digits = 1` is immune.**
Verified before designing anything:

```
set extra_float_digits = -3;
select t9.plain();    -- 0.333333333333        (12 digits — wrong)
select t9.pinned();   -- 0.3333333333333333    (16 digits — right, at efd -3)
```

**But a `float8` return is not, and cannot be.** The float8→text conversion happens in the *client
protocol*, after the function has returned, under the session's setting:

```
set extra_float_digits = -3;
select t9.f8_pinned();   -- 1.78716970604e+12   — the function's own SET cannot save it
```

So immunity is available **exactly where the value is turned into `jsonb`**, and nowhere else.

## 3. Scope

- **`xpr.j(float8) → jsonb`**, `IMMUTABLE`, carrying `SET extra_float_digits = 1`. The immune
  conversion point. Any caller that renders through it is correct at any session setting.
- **`xpr.assert_float_digits()`**, raising a **named** refusal (`XPR03`) when the session is not
  pinned. For callers that hand back `float8` directly, which no wrapper can protect — the honest
  answer there is to refuse, not to return a short number.
- **Tests** proving `xpr.j` is immune at 1, 0 and −3 while bare `to_jsonb` is not, and that the
  guard fires and names itself.

## 4. Out of scope, and why — the part that matters

**The demo's compiled queries are NOT routed through `xpr.j` by this ticket.** They emit
`to_jsonb(<float8>)` inline, and that emission comes from
**`spikes/T-1/proto/compile.py`, which the demo loads directly and which is FROZEN EVIDENCE** — its
sha256 `b71b153802d0df94…` is cited in T-6's attestation and in all 42 battery outputs. It cannot be
edited, exactly as `runtime.sql` could not be before T-8 gave it a home.

**So the compiler needs the same promotion the runtime just got, and that is its own ticket** (§6).
Until then the demo is protected the way it already was — `demo/server/db.py` sets the GUC in the
connection options, executes `SET`, reads it back, and refuses to serve if it does not match. That
is real protection; it is just protection by *convention at the edge* rather than by construction.

## 5. Acceptance criteria

- **AC-1** — `xpr.j(float8)` returns identical `jsonb` at efd 1, 0 and −3, for a value with digits to
  lose. *Test:* all three settings, one connection each.
- **AC-2** — bare `to_jsonb` on the same value **does** move. *Test:* the same three settings — the
  control that proves AC-1 measures something.
- **AC-3** — `xpr.assert_float_digits()` raises `XPR03` when the session is not 1, and returns
  quietly when it is. *Test:* both directions.
- **AC-4** — the schema still installs 21 + 2 = **23** functions, and everything T-8 asserted still
  holds. *Test:* the existing `runtime/tests` suite, unchanged, plus the count.
- **AC-5** — the demo suite stays green. *Test:* `./run-demo test`.

## 6. What this ticket must spawn

**Promote the compiler out of the frozen spike**, the way T-8 promoted the runtime, and route its
`to_jsonb(<float8>)` emission through `xpr.j`. Only that makes the immunity reach the generated
queries. Until it lands, `xpr.j` is available and unused by the demo — and this spec says so rather
than implying the problem is closed.
