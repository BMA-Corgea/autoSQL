| **`MAX_SCAN` / the 20,000-row cap** | GIMS's dashboard code stops after examining 20,000 rows and flags the widget "Result capped for performance". This demo deliberately stays under it (Q21). |

| **alias** | The name a person gives an output column — the `alive` in operation 2's `alive = $.status == "ok"`. It is user-typed text that has to end up inside the SQL text, because SQL has no other way to name a column; §4.10 rules what is allowed there. |
| **the two GIMS checkouts** | The two copies of GIMS on this machine, both **siblings of this repository**: `../GIMS-Project` (the standalone tree, where Q12 puts the integration work) and `../GUTS/spine/L1-memory/gims-ledger` (the copy inside the GUTS spine, which Q12 leaves alone). Full paths, what is read from each, and what happens when one is missing: §9.7. |
| **contract-surface** | A count of what a language's *published surface* holds — how many of its constructs, or of the fixture cases that exercise them, fall inside some rule. It is **not** a count of what anybody actually does: no corpus of the expressions GIMS's tenants really write exists in either checkout (`FINDINGS.md` §5.7(i), and the same file's "What it is not"). So "68 of 130" means *this much of the test file is inside the subset*, and never *this much of real use is covered*. §12's AC-19 turns entirely on that distinction. |
| **`lag()`** | A **window function** (above) — and the entire mechanism of operation 9, which is why it is glossed rather than left to be guessed. For each row, `lag(x)` hands you the value `x` had on the **previous** row of the same partition, in the frame's order; on the first row of a partition there is no previous row, so it hands you NULL. "Did this beat differ from the one before it" is therefore `lag(value) IS DISTINCT FROM value`, one expression, no loop. Nothing in GIMS does this, and Python's standard library has no equivalent — §7.1's comparison rule says how the Python pane walks the rows itself instead. |
| **`date_trunc`** | A Postgres function that chops a timestamp down to the start of a unit: `date_trunc('day', …)` turns `2026-08-19 14:37:02` into `2026-08-19 00:00:00`. It is how operation 7 turns 8,400 individual beats into 7 days. |
| **`timestamptz` / `timestamp`** | Postgres's two timestamp types. **`timestamptz`** knows it is a real instant on a world clock, and prints itself in whatever time zone the session is set to. Plain **`timestamp`** is a wall-clock reading with no zone attached at all — cast a text timestamp ending in `Z` into it and the `Z` is parsed and then *silently dropped*. Which of the two a JSON timestamp is cast into changes what `date_trunc` answers, which is why §7.1's time-bucket rule pins it. |
| **the session time zone (`TimeZone`)** | A Postgres session setting naming the time zone that session works in. It decides **where a day starts**, so two sessions set differently put the same row in different day buckets while both are behaving correctly. Pinned to `UTC` by §7.1's time-bucket rule, for the same kind of reason §4.9 pins the digit setting. |
| **GIN index** | A Postgres index type built for values that have many parts inside them — a jsonb document, a text document's words. On a jsonb column it indexes the keys and values *inside* each record, so a query can find "the records whose `status` is `ok`" without reading every record. §4.8 forbids it, and every other index, for generated queries. |
| **DSN** | *Data source name* — the single string that tells a database driver where to connect and as whom: `host=127.0.0.1 port=55440 user=… dbname=…`. §11.2 turns on the demo being unable to produce one that points anywhere but its own container. |
| **synchronised sequential scan** | Postgres reading a whole table from top to bottom is a *sequential scan*. When a second one starts while the first is still running, Postgres **joins it onto the first wherever the first has already reached**, then wraps around to the top — so the second scan reads the same rows starting from a different place. Two runs of the identical query can therefore return the same rows in a different order, with nothing about the data having changed. It is one of the reasons §7.4 insists that every result carry an `ORDER BY`. |
| **collation** | The rule a database uses to decide which of two pieces of text sorts first. The **`C`** collation compares raw bytes. A language collation such as `en_US.UTF-8` follows dictionary conventions and can, for instance, ignore punctuation on its first pass — so the same two strings can sort in opposite orders under the two. Python compares strings by Unicode code point, which matches `C` and not the others; §7.4 pins `C` for exactly that reason. |
| **`jsonb_object_keys`** | A Postgres function that lists the top-level key names inside one jsonb value. Run across a whole collection it yields that collection's field-name vocabulary — which is how §4.10 knows the names a computed column must not collide with; §4.10 also says when the demo runs it. |
| **a ruling on delegated authority** | A decision *this document* made because Evan handed the decision over rather than one he made himself. Always labelled as such, always shown with its derivation from his own recorded words, and always overturnable by him in one line. §14.1 collects them. |

records, so Evan can watch the tool write SQL before any of this goes near GIMS.

> "we're going to need to see the SQL UI before we ever integrate this back into the GIMS, so make

*"Yes, but only after the demo"*. So this ticket is the thing standing between the project and
GIMS.

SQL for that pick, the SQL is shown in full, and the number it returns is checkable on the spot.
It is not a performance argument (§6), not an integration (§6), and not a mockup.

## 4. The safe subset — what the demo is allowed to compile

### 4.1 What Q18 actually released

His option, in full, as it was put to him:

> **Green light, but only the safe operations** — The demo starts, but everything it generates is
> confined to the slice of GIMS’s expression language the investigation checked and corrected —
> 32 of 48 building blocks, covering 68 of the 130 test cases, with the other 62 refused out loud —
> and that slice is not clean either: the one defect measured inside it makes 8 of the 16 expression
> paths it can reach give wrong answers, one of them returning 1 where Python returns 1e+300.

Both halves of that are binding: the subset **and** the acknowledgement that the subset is not clean.

### 4.2 The subset, exactly

Taken from `spikes/T-1/FINDINGS.md` §5.7, which is the only place it is defined, and reproduced
mechanically by `spikes/T-1/proto/closure_subset_coverage.py` → `spikes/T-1/analysis/subset-coverage.json`.

**Allowed — 32 of 48 constructs:**

- all **10** leaf and structural node types — `num`, `str`, `bool`, `null`, `field`, `neg`, `not`,
  `and`, `or`, `call` (the AST tag universe is 12; `cmp` and `bin` are counted below as their
  operators, per the construct census in `f2` §2.1 — `f2` is T-1 shorthand for one of the
  investigation's sub-reports, and §2.1 is the place that counts the language at 48);
- **4** of the 5 arithmetic operators: `+` `-` `*` `/`;
- all **6** comparisons: `==` `!=` `<` `<=` `>` `>=`;
- all **5** field-path forms — the bare `$`, `.ident`, `["quoted"]`, `[n]`, `[-n]`
  (`expr.py:215-246`) — with a compile-time check that any literal array index satisfies
  `|index| < 2³¹`;
- **7** of the 22 functions: `abs` `coalesce` `count` `if` `length` `max` `min`.

**Refused, out loud — the other 16 constructs**, named individually because a test has to be able to
try each one:

| kind | the refused constructs |
|---|---|
| operator (1) | `%` |
| rounding functions (3) | `round`, `floor`, `ceil` |
| aggregate functions (2) | `sum`, `avg` |
| conversion functions (2) | `string`, `number` |
| string functions (4) | `concat`, `contains`, `lower`, `upper` |
| date functions (4) | `today`, `now`, `days_between`, `date_add` |

The arithmetic is auditable: 48 − 12 functions the panel already excluded = 36; − `round`/`floor`/`ceil`
= 33; − `%` = 32 (`subset-coverage.json → subset_definition.corrected_construct_count`).

**One clause is not on either list, because it is not a construct.** `FINDINGS.md` §5.7's subset also
carries a *qualifier*: `==` and `!=` are restricted "over container operands". `==` and `!=`
themselves stay in — the qualifier removes no construct from the count of 32. What it restricts, when
it restricts it, and which of three defensible readings this spec takes, is §4.6. It is a runtime
rule, not a subset rule, and §4.3 explains why that distinction is forced rather than chosen.

**Coverage:** 68 of GIMS's 130 fixture cases (52.3%). The other 62 are refused. Do not quote 64.6%
or 84/130 — that is the uncorrected figure, and `FINDINGS.md` §5.7 says so in terms. §12's AC-19
records what the demo does with that number, and why it is an observation rather than a pass mark.

### 4.3 Why enforcement takes two layers — and why `Uncompilable` is not one of them

**Correction to an earlier draft of this spec, and the reason this section exists.** It said the demo
stays inside the subset by surfacing the compiler's existing `Uncompilable` exception
(`compile.py:54`). **That does not work, and shipping it would have made the demo do the exact thing
the demo exists to disprove.** Verified by opening the file:

- `compile.py` implements a compilation method for **all 22** builtins —
  `grep -c "^    def _f_" spikes/T-1/proto/compile.py` returns **22**, and the names are `today now
  days_between date_add coalesce if lower upper contains number string concat length abs floor ceil
  round count sum avg min max`. Fifteen of those are outside the subset.
- It also compiles `%`, at `compile.py:289-293`, into `xpr.fmod` — the branch opens at `:289`
  (`if op == "%":`) and emits `to_jsonb(xpr.fmod(…))` at `:293`.
- `Uncompilable` is raised only for things the *language does not have*: an unknown AST tag
  (`:200`), an unknown field-path step (`:237`), an unknown comparison operator (`:274`), an unknown
  arithmetic operator (`:294`), a builtin with no `_f_` method (`:301`), a non-AST input (`:194`), a
  numeric literal that overflows to infinity (`:207`), and the generated-SQL size cap (`:173`).

Every one of the 16 refused constructs is a construct the language **does** have and the compiler
**does** implement, so not one of them reaches any of those raises. Walkthrough step 10 types
`round($.payload.load, 1)` and expects a refusal; under the old wording it would have compiled, run,
and printed a number.

**So enforcement is the demo's own job, and it takes two layers, because there are two kinds of
thing to catch.**

- **Some things can be known from the expression alone.** That `round` appears in
  `round($.payload.load, 1)` is visible in the text, before any data is touched, before any SQL
  exists. Anything of that kind is caught by **layer 1, the static gate** (§4.4), and nothing runs.
- **Some things are properties of the row and cannot be known until the query runs.** Whether
  `$.where` holds an object, or whether `$.huge` holds a number too large for the database to
  represent, depends on which record you are looking at. No amount of reading the expression settles
  it. `FINDINGS.md` §5.7 says this in its own words about the `==`/`!=` clause — whether an operand
  *is* a container is "a property of the **row**, not the AST". Anything of that kind is caught by
  **layer 2, the runtime refusal** (§4.5).

A single mechanism cannot do both, and pretending otherwise is what produced the defect this section
corrects. The order is fixed: **gate → compile → runtime probes → execute.**

**Refusal is a visible event, not a fallback.** Whichever layer refuses, the person sees it, it names
what caused it, and no wrong number ever appears. The phrase *"refused out loud"* is Q18's own — it
is quoted from the option he ticked, at §4.1, and reproduced in his lower case. There is
no quiet fallback to Python in this demo; where a fallback happens it is labelled, and §4.5 says
exactly what that means on screen.

### 4.4 Layer 1 — the static gate

**This is new code, it is safety-critical, and it is the only thing standing between the demo and the
fifteen out-of-subset functions `compile.py` will otherwise happily compile.** It gets its own file,
`demo/gate.py`, and its own row in §7.3's division-of-labour table.

**What it is.** One function, `gate(ast)`, that walks the parsed expression tree and either returns
quietly or raises `Refused(construct, why)`. It is called on the AST of **every expression the person
types** — operation 2's computed columns and operation 3's filter.

**Correction: those are the only two places an *expression* enters, and an earlier draft of this
section wrongly said they were the only two places *user text* enters.** Its words were "and on
nothing else, because those are the only two places user-written expression text enters the demo",
which reads as a claim that everything a person can type is gated. It is not, and this document's own
criteria say so: **AC-28 types a JSON field name containing a quote and a semicolon** — a third thing
typed, arriving *inside* an expression but checked by a different mechanism — and AC-38 types a column
name, which is a fourth. A safety claim that undercounts its own inputs is how one of them gets
shipped unchecked, so every place user text can enter is enumerated here, and each names what actually
checks it:

| # | what the person types or chooses | where it ends up | what checks it |
|---|---|---|---|
| 1 | **The computed-column expression** (op 2, right of the `=`) | compiled by `compile.py` into the `SELECT` list | **the gate** — construct by construct, this section. AC-14 |
| 2 | **The filter expression** (op 3) | compiled into the `WHERE` clause | **the gate** — the same call, the same allowlist. AC-14 |
| 3 | **A JSON field name inside 1 or 2** — e.g. `$["a\";b"]` | a **bind parameter**, never SQL text: `_t_field` calls `self._bind(key, 'text')` (`compile.py:222-240`) | the gate's field-path row (one of the five forms; `\|index\| < 2³¹` for a literal index), then the compiler's binding. **AC-28** |
| 4 | **The computed-column alias** (op 2, left of the `=`) | **SQL text** — SQL has no bind-parameter position for a column name | **§4.10's allowlist**, in the same `demo/gate.py`, run before emission. **AC-38** |
| 5 | **The row cap** (op 5) | a bind parameter in `LIMIT` | the query builder parses it as an integer and range-checks it — a positive integer no greater than **20,000**, which is `MAX_SCAN` (§0), the number Q21's answer keeps the demo below; anything else is refused before a query is built |
| 6 | **The sort field** (op 4), the **aggregate's field** (op 6), the **rolling window's field** (op 8) | either a JSON field path — a bind parameter, as row 3 — or a **previously-defined alias**, which reaches `ORDER BY` / `GROUP BY` / the aggregate as SQL text | whichever it is: row 3's binding, or **§4.10's validator run again on the same string** — §4.10: *"Every place the alias is emitted runs the same check on the same string"* |
| 7 | **The source collection** (op 1), the **sort direction** (op 4), the **aggregate function** (op 6), the **bucket granularity** (op 7) | a bind parameter (the collection) or a fixed keyword (the rest) | a **closed set** — the value must be one the demo itself offered: the three seeded collection names, `asc`/`desc`, `count`/`sum`/`avg`/`min`/`max`, `hour`/`day`. Anything else never reaches the query builder |

So the accurate claim is the narrow one: **the gate reads expression trees, and rows 1 and 2 are the
only two places an expression tree comes from.** Rows 3–7 are user text too; each is checked by the
mechanism named beside it, and not one of them is checked by nothing. **AC-42** tests that every row
of this table has its named check and that the check can be shown firing.

**One entry has been struck from row 6 since an earlier draft, and striking it was the fix rather than
the loss.** Row 6 also listed **"operation 9's compared value"** as a place user text enters. It would
be one only if the person chose that value — and §7.1's comparison rule pins it as this demo's own
fixed choice, so the document asserted both things at once and **a build could not tell whether the
control existed**. It does not. §7.1's comparison rule now rules it explicitly fixed, **AC-40(e)**
asserts that the screen offers no picker for it, and there is consequently nothing here for AC-42 to
test. An inventory that lists an input which does not exist is as unusable as one that omits an input
which does — in opposite directions: the first sends a build to write a control nobody asked for, the
second ships an unchecked one.

**When it runs.** *Before* `compile_ast` is called. If it refuses, no SQL is generated, no statement
is prepared, and nothing is sent to the database. That ordering is the point: a refusal that happens
after the SQL has run is not a refusal.

**What it decides, and how.** An **allowlist**, walked node by node:

| node | accepted only if |
|---|---|
| the tag | it is one of the **twelve** tags `compile.py` dispatches on: `num` `str` `bool` `null` `field` `neg` `not` `and` `or` `cmp` `bin` `call` |
| an arithmetic node (tag `bin`) | its operator is one of `+` `-` `*` `/` — this row, not the tag row, is what refuses `%` |
| a comparison node (tag `cmp`) | its operator is one of the six: `==` `!=` `<` `<=` `>` `>=` |
| a field-path step | one of the five forms, and any literal array index satisfies `\|index\| < 2³¹` |
| a call (tag `call`) | its name is one of `abs` `coalesce` `count` `if` `length` `max` `min` |

Anything else is refused, **by name** — the message says which construct, so walkthrough step 10 can
read "`round` is outside the safe subset" rather than "invalid expression".

**Correction: twelve tags, not ten — and why getting this wrong would have broken the demo.** An
earlier draft of this table accepted a node only if its tag was "one of the 10 leaf/structural types
of §4.2". **That was wrong, and wrong in the safety core.** The AST has **twelve** tags, and `cmp`
and `bin` are not among the ten. §4.2 says so itself, parenthetically: the ten is a count of
*constructs*, in which comparisons and arithmetic are counted as their six and five *operators*
rather than as their two tags — that is how the census reaches 48. The compiler is the authority on
what tags actually exist, and it was opened to settle it: every jsonb-valued node goes through the
single dispatch `fn = getattr(self, f"_t_{tag}", None)` at `compile.py:196`, and the methods it can
find are exactly twelve — `_t_num` (`:204`), `_t_str` (`:212`), `_t_bool` (`:215`), `_t_null`
(`:218`), `_t_field` (`:222`), `_t_neg` (`:243`), `_t_not` (`:246`), `_t_and` (`:252`), `_t_or`
(`:255`), **`_t_cmp` (`:259`)**, **`_t_bin` (`:277`)** and `_t_call` (`:297`).

A gate that accepted only ten would have refused **every comparison and every piece of arithmetic in
the demo** — `$.status == "ok"` (walkthrough step 3), `$.status != "ok"` (step 4), `$.payload.load >
80` (§7.1's own example for operation 2), `$.a + 0` and `$.a * 1` (§5's divergence table), `$.huge *
1` (step 13). It would have refused them at the tag, before their operators were ever looked at, and
the demo would have had almost nothing left to demonstrate. That is the same class of over-refusal
§4.6 rejects reading B for — a control that refuses ordinary things trains its reader to ignore it —
arriving here by a different route.

**The tag row is therefore permissive on purpose, and the two rows under it do the confining.** `cmp`
and `bin` are accepted *as tags* and then held to their allowed operators: `+` `-` `*` `/` for `bin`,
so `%` is refused; all six for `cmp`, so none is refused there. That is exactly where the construct
count of §4.2 puts them, so the gate and the subset definition agree construct for construct rather
than only in total.

**Why an allowlist and not a list of the 16 to block.** A block-list of sixteen names goes stale the
moment GIMS's expression language grows a twenty-third function: the new one is not on the list, so
it is allowed, so `compile.py` compiles something nobody has checked. An allowlist fails closed —
the new function is simply not among the seven, and is refused until somebody deliberately adds it.
The subset is defined as a set of *permitted* constructs (§4.2); the gate is that definition executed.

**What it deliberately does not do.** It does not decide the `==`/`!=` container question. It cannot
— that is a row property (§4.3, §4.6) — and a gate that guessed would either refuse ordinary
comparisons or pass container comparisons through. It allows `==` and `!=` by construct and leaves
the qualifier to layer 2.

**It does not touch `compile.py`.** It sits in front of it. Q19 said the compiler is reused *as-is*
(§4.7), and AC-33 tests the file's checksum. The gate is a separate file that the compiler does not
know exists.

Its acceptance test is AC-14, and it is decidable construct by construct: 32 accepted, 16 refused,
at least one expression each.

### 4.5 Layer 2 — the runtime refusal

**What it is for.** Two conditions that the gate provably cannot decide, both of which would
otherwise produce a wrong number or a silent null on screen. When either fires, **the pick is
abandoned, the screen names the cause, and the SQL side shows no number.** A refusal is not a wrong
answer; a number would be.

**Member (a) — a value above the largest double the database can represent.**

This is already ruled. `spikes/T-1/EXPERIMENTS.md` §1.2 puts it up as an open question and closes it,
on delegated authority, 2026-08-21:

> **None of the three.** The divergence becomes a **reported runtime refusal**. The generated SQL
> detects the out-of-range condition *while it is running* and refuses loudly — it raises a named,
> catchable error instead of returning a number or a null — and the caller reports that as a fallback
> to the Python path. **The pass bar stays at zero wrong answers, because a reported refusal is not a
> wrong answer.**

The facts behind it, measured there on this machine: jsonb will legally store `1e400`
(`jsonb_typeof('1e400'::jsonb)` → `number`), Python's evaluator returns the float `inf` for it, and
Postgres has no JSON *number* meaning infinity — so `runtime.sql` answers `NULL` instead, which is
precisely the silent form `FRAMING.md` §5 forbids.

**This spec is consistent with that ruling in behaviour, and honest about differing in mechanism.**
The EXPERIMENTS ruling implements the refusal *inside* `runtime.sql`, by making `xpr.f8`'s and
`xpr.num`'s out-of-range branch `RAISE` instead of answering `NULL::float8`. **T-2 may not do that.**
Q19 fixes `runtime.sql` as-is, AC-33 checksums it, and the edit belongs to T-3 (Run 1), where Q7
explicitly permits editing the spike's code. So the demo gets the same behaviour by a different
route:

> **The out-of-range probe.** Before executing a pick, the demo asks the database one extra question
> over exactly the rows that pick will read: does any value that will reach a numeric context have
> magnitude ≥ `1.7976931348623157e+308`? The probe is built from the same subexpressions
> `compile.py` just compiled, so it asks about the operands the expression actually touches and no
> others. If any row answers yes, the pick is refused **before** the compiled SQL runs, the refusal
> is named on screen, and the SQL pane shows no number.

**The probe, written out as SQL.** Member (b) below was pinned as a literal expression and this one
was left as prose. Both are literal now, for one reason: a build that has to *invent* this expression
has an obvious wrong way to write it, and **the wrong way fails silently rather than loudly**. For
each compiled operand `<op>` that reaches a numeric context — `compile_ast` returns "a Postgres scalar
jsonb expression" (`compile.py:432`), so each one can be wrapped without touching the compiler — the
probe asks:

```sql
jsonb_typeof( <op> ) = 'number'
AND abs( ( <op> #>> '{}' )::numeric ) >= 1.7976931348623157e+308::numeric
```

over the same rows the pick will read, `OR`-ed across the operands. If any row answers true, the pick
is refused.

**The wrong way, named so a build cannot arrive at it by accident.** The probe reads the **raw jsonb**
and casts it through `numeric`. It must **never** be routed through `xpr.f8` or `xpr.num`. Those two
carry the shipped 297-digit guard, and what that guard does is **return NULL, not raise** —
`WHEN abs((j #>> '{}')::numeric) > 1797693…::numeric THEN NULL::float8` (`runtime.sql:33-34`; the same
shape again at `:51-53`, and `xpr.num` inherits the first one for numbers at `:48`). So a probe built
on `xpr.f8` would ask "is this value too big?" and be handed a **null for exactly the values that
are** — and `NULL >= anything` is null, never true. The probe would answer "nothing to refuse", the
pick would run, and the screen would show the silent null this whole section exists to prevent: a
guess here produces **a quiet null instead of a refusal**, which is the failure mode, not a near miss
of it. `numeric` has no such limit — it holds `1e400` exactly — which is why `runtime.sql` itself uses
that same `(j #>> '{}')::numeric` idiom to *test* the value it then declines to return.

**The threshold is the real limit, not the shipped guard, and the difference is deliberate.** The
guard literal in the shipped `runtime.sql` is **297 digits** — `1.797693134862316e+296`, counted
mechanically from the file — where the real limit needs **309**. The twelve decades between them are
§5's defect, and this demo leaves them strictly alone: refusing there would suppress exactly what
walkthrough step 11 exists to show.

**When T-3 lands the guard fix, this probe is deleted** and the demo catches the error off the query
instead. **SQLSTATE** is the five-character code Postgres attaches to every error it raises, so a
program can recognise *which* error happened without reading the English sentence beside it; the code
**`22003`** is the one that means **a number is out of range** — too big or too small for the type it
had to fit into. So "catch SQLSTATE `22003`" means "let the query fail, and recognise that particular
failure by its code". That is what EXPERIMENTS §1.2 describes. Recorded here as a temporary shape
forced by Q19, not as a design.

**Member (b) — `==` or `!=` where an operand actually turns out to be a container.**

Same machinery, different question. The gate hands layer 2 the list of `==`/`!=` operand
subexpressions it saw. `compile_ast` returns "a Postgres scalar jsonb expression"
(`compile.py:432`), so each operand can be wrapped without touching the compiler:

```sql
jsonb_typeof( <the compiled operand> ) IN ('object','array')
```

asked over the same rows. If any row answers yes, the pick is refused, named, and no number appears.
Why this is the right rule rather than refusing `==` by construct is §4.6.

**Both members abort the whole pick, not the offending row.** That is the conservative behaviour and
it is the same shape EXPERIMENTS §1.2 names for the ruled version: *"The refusal is therefore
per-widget, not per-row"* — one pathological row makes the entire widget fall back.

**What "a reported fallback" means on this screen, exactly.** The two layers differ, and the
difference is principled:

- **A layer-1 refusal**: the expression is outside the subset, so the demo declines the pick
  entirely. **Both panes stay empty.** Showing a Python number for a pick the demo has just declared
  out of scope would be answering a question it refused to accept.
- **A layer-2 refusal**: the expression *is* in the subset and the gate accepted it; the **data**
  made SQL unable to answer. This is exactly the "explicit fallback, instrument which path ran" case
  GA-3's note asks for. **The SQL pane shows the named refusal and its cause; the Python pane shows
  Python's answer, labelled as it always is.** Because Q24 put both panes on screen permanently,
  nobody can mistake the Python number for the SQL's — which is what makes the fallback *reported*
  rather than silent.

One display consequence: where Python's answer is `inf`, `-inf` or `nan`, the pane renders that text
literally. It must never be sent as a JSON null, because a null there is indistinguishable from the
very divergence §5 is about.

**Cost.** One extra query per pick, over at most 8,400 small rows. Reading whole collections is
affordable precisely because Q21 kept the database small, and §6 forbids any speed claim, so there is
no timing budget to blow.

### 4.6 The `==` / `!=` container rule — which reading, and where it is enforced

**RULING — a ruling on delegated authority, 2026-08-21.** Authority: GA-4, quoted in §2 and §14.1.

**What is ambiguous.** `FINDINGS.md` §5.7 restricts "`==`/`!=` over container operands" without
saying when that is decided. `subset-coverage.json` refuses to guess and measures all three
defensible readings:

| reading | what it means | fixture cases kept |
|---|---|---:|
| **A** | *runtime-witnessed* — a case is out only if some `==`/`!=` **actually received** a list or dict while the real evaluator ran it. Marked **PRIMARY**: "This is the clause as written." | **68** of 130 (52.3%) |
| **B** | *static over-approximation* — a case is out if any `==`/`!=` operand **could** be a container: a field reference, or `coalesce`/`if` over one. "This is what a compile-time AVOID rule could actually implement." | 62 of 130 (47.7%) |
| **C** | *maximal* — a case is out if it uses `==` or `!=` at all. "The floor." | 56 of 130 (43.1%) |

The file states the reason the readings differ at all: "Whether an operand IS a container is
therefore a property of the ROW, not of the AST, and a construct-keyed AVOID rule … cannot decide it
statically."

**What is at stake, concretely.** An earlier review of this spec noted that under **reading B**,
walkthrough steps 3 and 4 — `alive = $.status == "ok"` and the filter `$.status != "ok"` — would
**both be refused**, because `$.status` is a field reference and a field reference could resolve to a
container. That is not hypothetical on this data: §8.3's records genuinely carry object-valued keys
(the heartbeat `payload`, and the `{"code": …, "n": …}` extra keys `gen_data.py:46` already
produces). Reading B would refuse the single most ordinary thing a dashboard does, on data where
nothing actually goes wrong.

**The ruling.** Take **reading A's semantics, enforced in layer 2.**

- The **static gate allows `==` and `!=` by construct** (§4.4). It does not try to decide
  container-ness, because it cannot.
- The **runtime refuses the specific picks where an operand actually resolves to a container**
  (§4.5 member (b)).

**Why.** It falls straight out of the two layers, and each rival reading fails on something the
record already says:

- Reading A **is the clause as written**, and `subset-coverage.json` marks it PRIMARY for that
  reason. Nothing has to be reinterpreted to adopt it.
- Reading A was previously unimplementable only because there was one layer to implement it in. With
  a gate that reads the AST and a probe that reads the rows, each question goes to the layer that can
  answer it. The ambiguity was never about *what* the clause means; it was about *where* it can be
  enforced.
- Reading B refuses ordinary comparisons over a possibility. Spurious refusals train a reader to
  ignore refusals — which is the same failure mode §5 spends its whole length protecting against for
  disagreements. A control the reader has learned to skip is not a control.
- Reading C removes computed columns and filters from the demo almost entirely, and the demo's job
  (§1) is to show a person picking slices of data.
- **Container comparisons never return a wrong answer under this ruling** — they return a named
  refusal. That is the property that matters, and it is the one reading A's semantics guarantee.
- **The price on the fixture is zero.** Across all 130 cases `expr._eq` is called 16 times and never
  once on a list or a dict (`subset-coverage.json → self_check.eq_operand_kind_matrix`:
  `container_cells_touched` = 0). So the difference between A's 68 and B's 62 is six cases refused
  over a possibility that never materialises.

**How Evan overturns it, in one line.** *"Refuse `==` on any field reference"* switches the demo to
reading B: the gate takes over the clause, layer 2 member (b) is deleted, and walkthrough steps 3, 4
and 12 are rewritten. Nothing else changes. *"Refuse `==` entirely"* is reading C and removes steps
3 and 4 as well.

### 4.7 The compiler is reused unmodified (Q19)

`spikes/T-1/proto/compile.py` is imported as it stands. Three facts about that, all verified by
opening the file:

- It depends on nothing outside the Python standard library (`compile.py:42-45`), so reusing it
  drags no GIMS dependency in.
- Its interface is `compile_ast(ast, column="data", ctx_param="ctx") -> Compiled(sql, params)`
  (`compile.py:432`) — it returns one Postgres expression plus its bind parameters. It does **not**
  write a whole query. The surrounding `SELECT / FROM / WHERE / GROUP BY / ORDER BY / LIMIT` and the
  window functions are the demo's own SQL (§7.3).
- The T-1 spike's own ground rule was that nothing may ever import it. Q19 lifts that rule for this
  ticket and only this ticket. Its docstring's "THIS IS NOT A LIBRARY" line stays where it is; the
  demo adds a comment beside its import naming Q19 as the authority.

**The file is not edited.** If the build finds a defect in it, the defect is written down and left in
place, and the divergence shows up in the side-by-side where it belongs. Q19 said *as-is*.

Reusing it as-is is also what makes §4.4 necessary rather than optional: an unmodified compiler
compiles everything it knows how to compile, which is all 48 constructs, so the restriction to 32 has
to live somewhere else.

### 4.8 No indexes, ever (Q11)

No index is created to make any generated query faster. Not a **GIN index** on the jsonb column — the
Postgres index type meant for values with many parts inside them, which indexes the keys and values
*within* each jsonb record so a query can find "the records whose `status` is `ok`" without reading
every record (§0) — not an expression index, not one "just for the demo". Two independent reasons, both already on the record:

- Q11's recorded answer is *"Not acceptable — index work stays off"*.
- Four of the compiler's SQL helper functions are declared `IMMUTABLE` while actually reading a
  session setting. Postgres believes the declaration and will cache their results in an index; T-1
  measured the result — **the same query over the same 200 rows returned 0 rows with an index and
  200 rows without one** (Q10's briefing, from `FINDINGS.md` §1.2 / D17).

The table keeps its primary key, which is part of the table's definition rather than query
acceleration — ruled at §14.1 R6.

### 4.9 The Postgres digit setting (Q10)

Postgres has a session setting, `extra_float_digits`, controlling how many digits it prints when it
turns a floating-point number into text. T-1's whole 130/130 result was obtained at one value of it
(`1`, the modern default). Q10's answer did **not** make pinning it a permanent rule — it sent the
question to the correctness run (T-3) to test all three values.

So the demo does the modest thing: it sets `extra_float_digits = 1` on its own session, and the SQL
pane **displays the value it ran at**. It makes no claim that this is the rule. Evidence that this is
the value everything was measured at: `spikes/T-1/proto/coverage_probe.py:111`,
`spikes/T-1/proto/idxshape_immutable.sql:3`.

**It is one of exactly two session values the demo pins, and the other one matters more than this
one.** The second is the **session time zone**, set to `UTC`, ruled and derived at §7.1's time-bucket
rule and displayed beside this one in the SQL pane. They are named together here because a reader who
found a *digit* setting pinned, and the time zone left to whatever the container's environment
happened to supply, would reasonably conclude that the time zone did not matter — and it decides which
day bucket every row of operation 7 lands in. Both are **set** by the demo on every connection it
opens and **read back from nowhere**; §7.2 item 4 says the same thing from the arithmetic side.

### 4.10 The computed-column alias — the one place user-typed text reaches SQL text

**RULING — a ruling on delegated authority, 2026-08-21, derived from Q11.** Authority: GA-4 (§2,
§14.1). Collected as **R10** at §14.1.

**What the problem is, in plain terms.** Operation 2's syntax is GIMS's own:
`alive = $.status == "ok"`. Everything to the *right* of the `=` is an expression, and every value
and every JSON field name in it reaches Postgres as a **bind parameter** — handed over separately
from the SQL text, never pasted into it (§9.3, AC-28). The part to the *left* of the `=` is different.
It is a name the person typed, it names an output column, and **SQL has no bind-parameter position for
a column name**: `SELECT … AS %(name)s` is not valid SQL, in Postgres or anywhere else. So the alias
is either written into the SQL text or the column has no name the person would recognise. An earlier
draft of this spec said nothing about what was allowed there or how it was emitted, and that silence
is the defect this section closes.

**Why this is a Q11 question rather than a new one.** Q11 asked, in his own words,
*"do you accept the compiler writing tenant-supplied field names straight into the SQL text?"* His
answer was *"Not acceptable — index work stays off"*, and the option he ticked spells the mechanism
out: *"The compiler never writes field names into SQL text"*. In the same question he was offered,
and did not take, the middle option — *"Acceptable with a strict field-name check specified up
front"*. His objection was to tenant-supplied text reaching SQL literal position.

**An alias is not the same surface, and this spec says so rather than blurring it.** A field name in
literal position *addresses data* — it decides which rows and which values a query reaches. An alias
only *names a column on the way out*: it cannot select a row, reach a table, change a predicate or
widen what the query returns. So Q11's ruling does not automatically forbid it. But it is still
user-typed text in SQL text, which is the shape he objected to, and **a spec that stayed silent about
it would have quietly shipped the thing he refused.** Being narrower than the surface he ruled on is
a reason to be careful with it, not a licence to leave it undefined.

**The ruling.** The alias is **validated against a strict allowlist before it is emitted**, and
anything else is **refused loudly, by name**. It is never string-interpolated without that check
having passed.

- **The pattern, exactly:** `re.fullmatch(r"[A-Za-z_][A-Za-z0-9_]{0,62}", alias)`. ASCII letters,
  digits and underscore only; it must begin with a letter or an underscore; **1 to 63 characters**.
  **`re.fullmatch`, not `re.match`** — `re.match` anchors only the beginning, so
  `alive"; DROP TABLE demo.records; --` would pass it. This is written down as a pattern rather than
  as a description because a description is what a build re-derives differently.
- **Why 63.** It is Postgres's own identifier limit (`NAMEDATALEN` − 1). Anything longer is
  **truncated by the server** — it emits a `NOTICE` saying so, which no browser will ever put in
  front of him — so two aliases differing only past character 63 would collapse into one column and
  the two panes would disagree for a reason nobody could see on screen. Refusing is the honest
  answer; truncating is the one that manufactures a mystery.
- **What the pattern excludes, and why each exclusion earns its place.** Every quote character, so a
  double-quoted identifier cannot be closed early. Every space, semicolon and comment marker, so no
  second statement can be started. Every non-ASCII character, so no homoglyph and no Unicode
  normalisation surprise. And **`%`**, which is not a SQL hazard but a binding one: the compiler's
  parameter style is `%(name)s` (`compile.py:164`), and a stray `%` in the same statement breaks the
  binding of the very parameters that were keeping the *rest* of the pick safe. `compile.py:439-441`
  already notes that hazard about its own output and does nothing about it; the alias is the demo's
  own emission, so the demo handles it.
- **How an accepted alias is emitted:** double-quoted — `AS "alive"` — so it is case-preserving and
  can never be read as an SQL keyword. **The quoting is applied after the check, never instead of
  it.**
- **Every place the alias is emitted runs the same check on the same string.** Operation 2's column
  becomes selectable below, so one alias can also reach `ORDER BY` (op 4), `GROUP BY` (op 7) and the
  aggregate (op 6). There is one validator function and every emission calls it; none of them
  re-implements the rule.
- **Collisions are refused too, by name — and the list is longer than the table's own columns.** An
  alias is refused if it equals any of:
  - **`collection`, `key`, `data`** — the table's own columns (§8.2);
  - **`bucket`, `rolling_avg`, `changed`, `agg`** — the four column names **the demo's own query
    builder emits**, for the time bucket (op 7), the rolling window (op 8), the changed-rows flag
    (op 9) and the aggregate (op 6). They are pinned by those exact names in §7.3, so that this list
    can be a finite list rather than a description;
  - **every top-level JSON field name of the source collection** — read out of the data itself, not
    guessed: `sender_id`, `ts`, `status`, `payload` on `noun:Heartbeat`; `id`, `status`, `due_date`,
    `priority` and `field_0` … `field_14` on `noun:Sample`; the witness keys §8.3 names on
    `noun:EdgeCase`. **how the demo knows them, and when it reads them, is three paragraphs below**;
  - **an alias already defined in this pick.**

  **The second group was missing from an earlier draft, and that was an omission rather than a
  judgement.** The rationale the draft stated for the first group — two different things must not
  share one column name — applies to the builder's own emissions identically, and in fact more
  sharply: a person who names a computed column `bucket` and then buckets by day gets two `bucket`
  columns in one `SELECT`, every later reference resolves to whichever one Postgres resolves it to,
  the Python pane resolves its own dictionary key to the other, and **the two panes disagree over a
  naming accident** — a false disagreement, which §5 spends its whole length explaining is the one
  thing this screen must not manufacture. That is why §7.3 fixes the four emitted names instead of
  leaving them to the build: a list of forbidden names is only checkable if the emitted names are
  themselves fixed. **AC-38(a) tests one name from each group.**

  **The third group was missing too, and it is not one name but a whole namespace — the source
  collection's own field names.** This is the more dangerous omission of the two, because the other three are
  seven fixed strings and a duplicate check — things a reviewer can hold in their head — while this one
  is however many keys the chosen collection happens to carry. The mechanism is §7.1's operation 2 in its own words:
  a computed column *"becomes selectable below"*. So after `status = $.payload.load > 80` is typed on
  `noun:Heartbeat`, the field picker beneath it offers **two different things both called `status`**
  — the collection's real `status` field and the computed column — and the person choosing one for the
  sort (op 4), the aggregate (op 6) or the rolling window (op 8) cannot see which they got. Worse,
  §4.4 row 6 shows the two travel by **different routes**: a real field goes down as a JSON field path
  in a bind parameter, a computed column goes down as an alias in SQL text. **Each pane can resolve
  the same picked name to a different one of the two**, and then the screen shows a disagreement whose
  cause is a naming accident. That is a false disagreement inside the mechanism whose entire job is to
  make real disagreements unmissable (§5) — the same argument the second group already makes, over a
  much larger set of names.

  **Only the *top level* is on the list, and that is the whole surface rather than an approximation of
  it.** A nested field is reachable only as a path — `$.payload.load`, displayed as `payload.load` —
  and §4.10's pattern forbids `.`, so no alias this validator can accept is capable of colliding with
  a nested name. Top-level keys are exactly the names that can be spelled both ways. Keys that could
  not be aliases anyway — one containing a quote, one longer than 63 characters — are already refused
  by the pattern before the list is consulted, so the list only has to do work for the keys that would
  otherwise be legal.

  **How the demo knows the field names, and when it reads them.** There is no schema to read: §8.2's
  table stores each record as one opaque `jsonb` value, GIMS has no schema for these records either,
  and `noun:Sample`'s rows deliberately carry a *different* subset of `field_0` … `field_14` from one
  row to the next (`gen_data.py:34-46`), so **no single row's keys are the collection's keys**. The
  demo therefore **reads them out of the data**, as the union over the whole collection:

  ```sql
  SELECT DISTINCT k
    FROM demo.records, LATERAL jsonb_object_keys(data) AS k
   WHERE collection = %(collection)s
   ORDER BY k
  ```

  **`jsonb_object_keys`** is glossed at §0. The collection is a bind parameter, as it is everywhere
  else. **When:** at **operation 1** — the moment a source collection is chosen, *before* the field
  picker below it is drawn and *before* any alias is validated against anything. Once per collection,
  cached under the collection name for the session, re-read when the collection changes; not per
  keystroke and not per pick. **The server computes it once and hands the same list to both panes**,
  because §4.10's rule is that the identical check runs on the identical string, and a check's input
  is part of the check: two panes reading two vocabularies would refuse different names.

  **Cost and freshness.** One query over one collection of at most 8,400 small rows, which is
  affordable for the same reason §4.5's probes are (Q21 kept the data small, §6 forbids a speed
  claim). Nothing writes to `demo.records` while the demo runs except AC-23(a)'s deliberate mutation,
  which changes a *value* and not the key set, and the seed is deterministic (§8.4) — so a list read at
  source-selection time is still correct at pick time. Re-reading on every change of source is
  specified anyway, because it costs nothing and removes the question.

  **What this changes about the walkthrough: nothing.** `alive` (steps 3 and 14), `busy`, `days_left`
  and `pct_ok` are none of them field names of any seeded collection. What becomes newly refused is a
  computed column named `status`, `ts`, `payload` or `sender_id` on the heartbeat — and the refusal
  names the collision, so the person renames it and moves on. **AC-45** tests it, including the part
  that cannot be tested by a fixed list: that the names come from the data.
- **The Python pane applies the identical check to the identical string**, so a name refused on one
  side is refused on both, and an accepted name keys the same column in both. A check on only one
  side would be a false disagreement generator (§7.1's window rule makes the same argument about
  frames).

**Why an allowlist rather than escaping.** Escaping asks *"is there any input I have failed to
neutralise?"* — an open-ended question, answered wrongly the first time a case is missed, and the
cases here are genuinely confusable: the doubling rule inside a quoted **identifier** is not the same
as the one inside a quoted **literal**, and code that handles both mixes them up eventually. An
allowlist asks *"is this input one of the shapes already known to be safe?"* Everything unanticipated
— every future Unicode form, every driver quirk, every escaping subtlety nobody thought of — lands
outside it and is refused. It **fails closed**, which is the same argument §4.4 makes for the static
gate, and it puts the rule at spec time rather than build time, which is what Q11's middle option was
asking for. It costs nothing real: `alive`, `busy`, `days_left`, `pct_ok` are all already inside the
pattern.

**What a refusal looks like.** The same shape as a layer-1 refusal (§4.4, §9.3): the pick is declined
**before any SQL exists**, nothing is sent to the database, **both panes stay empty**, and the message
names the alias and the rule — *"`alive"; DROP TABLE demo.records; --` is not a usable column name:
letters, digits and underscore only, starting with a letter or underscore, at most 63 characters."*
It never says "invalid input".

**Its acceptance criterion is AC-38**, which feeds the validator hostile input on purpose, and
**walkthrough step 14** is Evan driving the same refusal himself — the document's standard everywhere
else is that a control is demonstrated firing, not merely specified (§5, §8.3's R11).

**How Evan overturns it, in one line.** *"Don't put my column names in the SQL at all"* replaces the
emitted alias with a generated one — `c1`, `c2`, … — and maps his name back on in the browser; the
cost is that the SQL pane then reads `AS c1` where he typed `alive`, which works against §1's claim
that the SQL on screen is the query. *"Let me use any name I like"* removes the check, and with it
this spec's consistency with Q11.

## 5. The one thing that must not be cut

**Reusing the throwaway compiler is only safe because the screen shows both answers.**

This section exists because those two decisions — Q19 and Q24 — were answered separately and read
like separate features. They are not. Q19 is safe *because of* Q24, and unsafe without it.

Here is the chain, in plain words.

**One.** The compiler being reused has known cases where its SQL disagrees with Python. This is not a
suspicion; it is measured, and the measurement is in this repo at
`spikes/T-1/analysis/fuzz/A_f8_guard.txt`. Twenty expression paths were run against records holding
one ordinary value — `1e300`. **Sixteen of the twenty disagreed.**

**Two.** The safe subset does not exclude them. Eight of those sixteen disagreements are built
entirely from constructs the subset keeps:

| The expression | Python says | The SQL says |
|---|---|---|
| `$.a + 0` | `1e+300` | *nothing — a null* |
| `$.a * 1` | `1e+300` | *nothing — a null* |
| `- $.a` | `-1e+300` | *nothing — a null* |
| `abs($.a)` | `1e+300` | *nothing — a null* |
| `$.a < 1e301` | `True` | *nothing — a null* |
| `$.a > 1` | `True` | *nothing — a null* |
| `$.a >= $.a` | `True` | *nothing — a null* |
| **`max($.l)`** | **`1e+300`** | **`1`** |

The record is unremarkable: `a = 1e300`, `l = [1e300, 1]`. `1e300` is an ordinary finite number, well
inside what the column can hold — not an infinity, not a corruption.

**Three.** The last row is the one that matters. Seven of the eight return *nothing*, which at least
looks wrong on a screen. The eighth returns **`1`** where the true answer is **`1e+300`** — a
plausible, quiet, completely wrong number. `max` is one of the seven functions the subset keeps.

**Four.** The cause is known, and it is not being fixed here. A guard inside
`spikes/T-1/proto/runtime.sql` is written as a **297-digit** number where it should be **309** —
counted mechanically from the file — so it rejects every value above `1.797693134862316e+296`
instead of the real limit `1.7976931348623157e+308`, about 12 of the 632 decades a float can hold.
`FINDINGS.md` §5.8(c) records that the too-small guard is *why* addition, subtraction and `sum()`
cannot overflow today — *"an accident of defect #1, not a design"* — so correcting the digits would
convert today's silently wrong answers into hard out-of-range errors — SQLSTATE `22003`, glossed at
§0 and §4.5.

**What that conversion costs is disputed, and this spec does not lean on the disputed figure.**
`FINDINGS.md` prices the recovery path at **+463%** on a constructed worst case and quotes it eleven
times. `RECHECK-2026-08-21.md` §3.3 struck it: the number rests entirely on
`probes.json → poison_syncscan.off.median_ms = 6916.85`, an orphan data block with **no surviving
producer** and no surviving corpus, and the identical claim prices at **+2.2%** from the numbers that
were retained. So the honest statement of the record today is *disputed, not measured*, and
**+463% may not be used as an argument here.** It is not needed: **Q19 said reuse it as-is**, and
that instruction carries this section on its own. Pricing the fix properly is T-3's job — where
EXPERIMENTS §1.2 has already ruled what the fixed guard turns into (a reported runtime refusal,
§4.5), which is a considerably smaller thing than "+463%" made it sound. **The defect ships.**

**Five.** Therefore the side-by-side is the control. With both answers on screen, `max($.l)` shows
`1e+300` on one side and `1` on the other, and a person sees a disagreement. With one answer on
screen, it shows `1`, and a person sees a number.

**This is a correctness control, not a feature.** It does not get cut for time, it does not get
deferred to "phase 2", and it does not get replaced by a list of expected answers in a document. If
it is dropped, the demo becomes a machine that displays confident wrong numbers — the exact failure
this whole project exists to prevent, staged as a demonstration of success.

The acceptance criteria enforce this three ways: the two panes are always both populated (AC-20), a
disagreement is flagged rather than shown quietly (AC-21), and the walkthrough contains a step whose
**expected outcome is a visible disagreement** (AC-22, walkthrough step 11). That last one is what
proves the control actually works rather than merely existing.

> #### THE WINDOW RULE — the frame operations 8 and 9 share, and what a short window returns
>
> **A ruling on delegated authority, 2026-08-21.** Authority: GA-4 (§2, §14.1). Collected as **R9**
> at §14.1.
>
> **Why this has to be pinned and not described.** Operation 9's row above already pins a convention
> of exactly this kind — *"Each sender's first beat has no predecessor and is always kept; both panes
> apply that same convention"*. Operation 8 needs the same thing and an earlier draft of this spec
> left it as a bare `ROWS BETWEEN` in §7.3. A 3-point trailing window has **one** row to work with at
> a sender's first beat and **two** at its second, and there are at least three defensible answers
> then: average what is there, return nothing, or divide by 3 anyway. If the SQL pane picks one and
> the Python pane picks another, walkthrough step 8 shows a **disagreement that means nothing** — on
> the first two rows of all 50 senders, and on nothing else. That is a **false disagreement**, and §5
> spends its whole length explaining why one of those is the single most damaging thing this screen
> can produce: it is what teaches a reader to skim past the real one.
>
> **The frame, written once and used by both operations — and written so that it runs.**
>
> ```sql
> OVER (PARTITION BY (data ->> 'sender_id')
>       ORDER BY     (data ->> 'ts'), key)
> ```
>
> The `key` tiebreak is there for the reason §7.4 gives it, so the row order inside one sender is
> defined even if two beats ever share a `ts`. Operation 8 adds
> `ROWS BETWEEN 2 PRECEDING AND CURRENT ROW`; operation 9 reads **`lag()`** (§0 — for each row, the
> value the previous row of the same partition held) over the same ordering.
>
> **Correction: an earlier draft wrote this frame as `PARTITION BY sender_id ORDER BY ts, key`, and
> that form would not run.** §8.2's table has exactly three columns — `collection`, `key` and `data`
> — and there is no `sender_id` column and no `ts` column anywhere in this database. Both live
> *inside* the jsonb (§8.3), so both have to be read out of it with `->>`, exactly as the comparison
> rule below already writes them. The two forms appeared in one document for one frame; a build
> reading the wrong one gets `ERROR: column "sender_id" does not exist` and has to invent the fix,
> and what it invents is where the two panes start to differ. Every occurrence in this document is
> now the runnable one.
>
> **`->>` returns text, and both components are compared as text on purpose.** `sender_id` is text
> already. `ts` is fixed-width UTC ISO-8601 (§7.1's comparison rule), the form in which text order
> *is* time order — so neither pane has to parse a date to reach the same sequence. The comparison is
> under the `C` collation (§0, pinned at §7.4), so it is byte order on both sides.
>
> **What operation 8 returns at a short window.** The average is over **the rows that exist**, never
> over a phantom three:
>
> | row within one sender | rows in the frame | the 3-point rolling average of `$.payload.load` returns |
> |---|---:|---|
> | row 1 — the sender's first beat | 1 | its own `load`, if that value is non-null, ÷ **the number of non-null values in the frame** — 1 here. **Never null**, unless that single value is itself null |
> | row 2 | 2 | (the non-null `load`s among rows 1–2, summed) ÷ **the number of them** — 2 when both are present |
> | row 3 and every row after | 3 | (the non-null `load`s in the frame, summed) ÷ **the number of them** — 3 when all three are present, which on the seeded data is every row |
>
> **The divisor column is written the long way on purpose.** An earlier draft's third row read simply
> "÷ **3**", which is true of the seeded data and false as a rule — it agrees with the sentence below
> only because §8.3's `payload.load` is always present. A build reading the table alone would have
> implemented the constant 3; the rule below is what it must implement, and the table now says the
> same thing rather than a special case of it.
>
> **The rule both sides implement, stated so neither can drift:** *the divisor is the number of rows
> actually in the frame whose value is non-null, recounted for every row — never the constant 3.* If
> every row in a frame has a null value the cell is null, and both panes print `null` rather than a
> zero. No row is dropped and no row is padded.
>
> **The SQL side gets this for free; the Python side is the one that has to be written to match.**
> Postgres's own `avg(…) OVER (… ROWS BETWEEN 2 PRECEDING AND CURRENT ROW)` already averages exactly
> the rows in the frame and already ignores nulls in the divisor, so operation 8's SQL needs no
> special case. The Python reference does. A Python implementation that divides by 3 always, or that
> emits `None` until three rows have accumulated, disagrees with the SQL on rows 1 and 2 of every one
> of the 50 senders — 100 wrong cells — and agrees everywhere else, which is precisely the shape that
> looks like a real finding and is not one. **AC-24(d) tests each of the three cases separately, on
> each pane separately, before comparing them.**
>
> §7.2's exact-decimal rule applies to each of these divisions unchanged: accumulate in `numeric` /
> `decimal.Decimal`, then round half-up to 6 decimal places. Rows 1 and 2 round trivially — ÷ 1 and
> ÷ 2 of integers terminate — and row 3 onward is the non-terminating ÷ 3 that step 8 exists to
> exercise.
>
> **How Evan overturns it, in one line.** *"Leave the first two beats blank"* makes rows 1 and 2 null
> on both sides instead. The walkthrough's step-8 numbers regenerate from the seed and nothing else in
> this document changes.

> #### THE COMPARISON RULE — what operation 9 compares, and what it must not
>
> **A ruling on delegated authority, 2026-08-21.** Authority: GA-4 (§2, §14.1). Collected as **R13**
> at §14.1.
>
> **What was ambiguous, and why leaving it so would have wasted the build.** §7.1's operation-9 row,
> §7.3's division-of-labour table and §14.1's R1 all wrote `lag(…)` with an ellipsis, and not one of
> them said **which value** is compared against the previous row's. The obvious reading — the whole
> record — is the one that makes the operation useless, and it fails **silently**. Every heartbeat
> carries its own `ts`, and every `ts` differs from the one before it, so "keep only the rows that
> changed" would keep **all 8,400 rows**. The screen would show a filter that filtered nothing; both
> panes, implementing the same wrong thing, would **agree with each other perfectly**; §5's control
> would stay green; and the operation Evan asked for in prose would have been built, shipped and
> demonstrated doing nothing whatsoever. Nothing in the earlier draft could have caught that, which is
> precisely why it now has a criterion that can.
>
> **The general rule.** Operation 9 compares **one value per row**, and **the ordering key is excluded
> from that value by construction**. The ordering key is what puts the rows into a sequence; a
> sequence whose ordering key changes at every step is what a sequence *is*. Allowing it to also count
> as a change makes the operation a no-op by definition. The exclusion is therefore structural — it is
> not a preference about this particular data, and it holds whatever the compared value is and
> whatever key the rows are ordered by.
>
> **Which value that is, is fixed by this document. It is not something the person picks, and there is
> no control for it on the screen.** An earlier draft said both things at once: this paragraph said
> *"the value the person selects"*, §4.4's inventory listed "operation 9's compared value" as a sixth
> place user text enters — checked by a binding or by the alias validator — while the paragraph below
> pinned the value as this demo's own choice. **A build cannot tell from that whether the control
> exists**, and the two readings need a different screen, a different acceptance criterion and
> different Python on the second pane. Ruled here, under the same GA-4 delegation as the rest of R13:
> **fixed, and no control.** Every mention now agrees — §4.4's row 6 no longer lists it and says why,
> §14.1's R13 reads *"the value this spec fixes"* rather than *"the value the person selects"*, and
> **AC-40(e)** asserts that no picker for it exists on the screen.
>
> **Why fixed rather than offered.** Q20's option-3 text is what put this operation in scope at all
> (R1), and it reads *"show only the rows whose value differs from the one before it"* — one value,
> named by the option, with no choice attached. Adding a chooser would be scope he was never shown, on
> the single operation this document had to rule into existence in the first place; and the overturn
> lines at the foot of this box already give him the change in one line without a control existing.
> *"Let me choose what it compares"* is the line that asks for the control instead, and it adds one
> row to §4.4's inventory table, one closed-set or field-path check beside it, and one case to AC-42.
>
> **The concrete value this demo compares.** Checked against §8.3, which is where the seeded record
> shape is fixed — Q22's four fields, `sender_id`, `ts`, `status` and `payload`, the last an object
> carrying an integer `load` and a short text `note`. The demo's selection is *the whole record minus
> its ordering key*, which on this table is one Postgres operator:
>
> ```sql
> lag( data - 'ts' ) OVER (PARTITION BY data ->> 'sender_id'
>                          ORDER BY     data ->> 'ts', key)
>   IS DISTINCT FROM ( data - 'ts' )
> ```
>
> `data - 'ts'` is jsonb key removal: it returns the record without its `ts`. On the heartbeat shape
> that leaves `sender_id`, `status` and `payload` — and `sender_id` cannot vary inside a partition it
> is the partition key of, so **what can actually differ is `status` and `payload`, compared
> jointly**. That is the operation Q22's data shape was invented to make visible. Jointly rather than
> one at a time is the point: a beat that keeps its `status` and moves its `payload.load` has changed,
> and so has a beat that keeps its payload and goes from `ok` to `warn`. **AC-8 already counts the
> same thing from the other side** — it asserts that consecutive beats match on `status` and `payload`
> in 88–92% of cases — so the seeded-data check and this comparison are two readings of one property.
>
> **Three details this expression pins, each a divergence if a build guesses instead:**
>
> - **`IS DISTINCT FROM`, never `<>`.** At a sender's first beat `lag(…)` is NULL, and `NULL <> x` is
>   NULL — not true — so a build using `<>` would **drop every sender's first beat**, contradicting
>   the convention operation 9's own row states. `IS DISTINCT FROM` treats NULL as a value unlike any
>   other, so "the first beat is always kept" falls out of the operator instead of needing a special
>   case that each pane could get differently.
> - **The comparison is over parsed values, never over serialised text.** jsonb stores object keys in
>   its own order and normalises numbers; Python's `json.dumps` does neither. Two equal records would
>   compare unequal if either pane compared strings. So the SQL side compares `jsonb` with `jsonb` and
>   the Python side compares the parsed `dict` with the parsed `dict` — both content equality, key
>   order irrelevant. §8.3's phrase *"byte-identical"* describes how the **seed writes** consecutive
>   records; it is not how the comparison works.
> - **`ts` is written by the seed in fixed-width UTC ISO-8601 — `YYYY-MM-DDTHH:MM:SSZ`.** In that form,
>   and only in that form, text order is time order. That is what lets both panes order on
>   `data ->> 'ts'` as text and reach the same sequence without either of them parsing a date, and
>   §7.4's total-order rule leans on the same property.
>
> **The Python pane implements the identical thing:** group by `sender_id`, sort by `(ts, key)`, walk
> each group in order, and keep a row when `{k: v for k, v in record.items() if k != "ts"}` differs
> from the previous row's same value — the first row of each group always kept.
>
> **What tests it, and why the test is that shape.** **AC-40** asserts the kept-row count lands in the
> band §8.3's repeat rate implies — **between 700 and 1,100 of 8,400** — and it exists because that is
> the assertion a wrong implementation cannot pass. Put `ts` back into the compared value and **all
> 8,400 rows are kept**: not a near miss but an eight-fold one, visible in a single integer, on data
> whose repeat rate AC-8 already pins independently. AC-40 also asserts the negative directly — two
> records differing only in `ts` are **not** kept — so the failure is named rather than merely counted.
>
> **How Evan overturns it, in one line.** *"Compare only the status"* narrows the compared value to
> `data -> 'status'`; the kept count falls to whatever the seed's status changes alone produce,
> `demo/expected-answers.json` regenerates, and AC-40's band moves with it. *"Compare the whole
> record, timestamp included"* restores the reading this ruling rejects — and the honest consequence,
> stated here so it cannot be a surprise later, is that operation 9 then keeps every row and shows
> nothing.

> #### THE WINDOW-SHAPE RULING — the width is 3, the window trails, and the calculation is a mean
>
> **A ruling on delegated authority, 2026-08-21.** Authority: GA-4 (§2, §14.1). Collected as **R14**
> at §14.1.
>
> **Why this is labelled.** §14.1's promise is that nothing in this document is unattributed, and
> **the number 3 is not his.** The option he ticked is headed *"That, plus time buckets and rolling
> windows"* and its text reads *"a rolling calculation across neighbouring rows"*
> (`QUESTIONS-FOR-EVAN.md:420`). His note beside it — *"I'd actually like both additions, so 2 & 3"* —
> adds operation 9 and says nothing about operation 8. **Nothing in either says how many rows, which
> direction they run in, or what is calculated over them.** An earlier draft wrote *"e.g. a 3-point rolling average"* in
> operation 8's row and *"a 3-point trailing window"* in the window rule above — an example in one
> place and an assertion in the other. **A build cannot tell from "e.g." whether the 3 is fixed, whether
> the screen must offer a width control, or whether 5 would also satisfy the spec**, and the window
> rule immediately above pins behaviour that only makes sense at a fixed width: its whole table is
> "divisor 1, then 2, then 3".
>
> **The ruling, in three parts, none of them adjustable from the screen.**
>
> - **The width is 3 rows.** Fixed. There is no width control, no dropdown and no text box for it.
> - **The window trails** — `ROWS BETWEEN 2 PRECEDING AND CURRENT ROW`: the current row and the two
>   before it, never a row after it. A *centred* window (1 preceding, 1 following) is the other
>   ordinary choice and it is not taken.
> - **The calculation is an arithmetic mean**, over the frame's non-null values, by §7.1's window
>   rule. Not a rolling sum, not a rolling min or max. Operation 8 offers one aggregate.
>
> What the person *does* choose is the field: one numeric field of the source, read by §7.2 item 5's
> numeric read. That is the whole of operation 8's user input, and §4.4 row 6 is where it is checked.
>
> **The derivation, from what he did write.**
>
> 1. **Three is the smallest width at which a rolling window is visibly doing something.** At width 2
>    the "average" of a row and its predecessor is indistinguishable at a glance from a smoothing
>    nobody would call a window; at 3 the walkthrough can show a value that is plainly neither this
>    row's nor the last row's. Q21 — *"Correct and readable only"* — makes *readable by eye* the
>    selection rule, and step 8 asks him to check five numbers **by hand**: at width 3 that is five
>    divisions by 1, 2, 3, 3, 3, which a person can actually do.
> 2. **Trailing rather than centred falls out of the same answer plus the data.** A trailing window
>    at row *n* depends only on rows he has already read down the screen, so a hand check runs top to
>    bottom. A centred window makes every row depend on one below it, and the *last* row of each of
>    the 50 senders becomes a second short-window case on top of the first two — three conventions to
>    pin instead of two, for nothing gained.
> 3. **A mean rather than a sum, min or max, because §5 needs the division.** §7.2's exact-decimal
>    rule exists because a non-terminating division is where the two panes can silently disagree, and
>    a rolling *average* of an integer field over 3 rows is exactly that division. A rolling sum
>    would exercise nothing the aggregate of operation 6 does not already exercise.
> 4. **Offering a width control would add scope he did not ask for**, and every extra width multiplies
>    the short-window conventions the window rule above has to pin and AC-24(d) has to test.
>
> **How Evan overturns it, in one line.** *"Make the window 5 wide"* changes the frame to
> `ROWS BETWEEN 4 PRECEDING AND CURRENT ROW`, extends the window rule's table to divisors 1–5,
> extends AC-24(d) to five cases, and regenerates step 8's hand-computed numbers. *"Let me pick the
> width on screen"* adds a control to §4.4's inventory table as a closed set (row 7's shape) and makes
> the window rule's table a rule over *n* instead of over 3. *"Give me a rolling sum as well"* adds a
> second aggregate to operation 8 and a second closed-set control.

> #### THE TIME-BUCKET RULE — the expression, the cast, the time zone and the label
>
> **A ruling on delegated authority, 2026-08-21.** Authority: GA-4 (§2, §14.1). Collected as **R15**
> at §14.1.
>
> **What was left undecided, and why that is the same defect that nearly shipped operation 9 doing
> nothing.** An earlier draft of §7.3 wrote operation 7 as `date_trunc('hour'|'day', …)` — an
> **ellipsis** where the bucketed value goes. Neither the expression nor its cast was pinned, and the
> **session time zone was pinned nowhere in this document at all**, while §4.9 pins a Postgres *digit*
> setting for a far smaller reason. Two panes filling in that ellipsis independently is how the same
> row lands in different buckets on each side, and the disagreement would look exactly like a real
> finding.
>
> **What is offered is his, and only what is offered is his.** Q20's ticked option names the
> granularities in its own text — *"grouping rows into time buckets (per hour, per day)"* — so `hour`
> and `day`, and nothing else, come from his answer and are a closed set at §4.4 row 7. Everything
> below is this spec's.
>
> **The expression, written out.**
>
> ```sql
> date_trunc('day', (data ->> 'ts')::timestamptz)   AS "bucket"
> ```
>
> with `'hour'` for the other granularity — a fixed keyword from §4.4 row 7's closed set, never user
> text. **`date_trunc`** is glossed at §0: it chops a timestamp down to the start of a unit.
>
> **Three things that expression pins, each of which is a divergence if a build guesses instead.**
>
> - **`data ->> 'ts'` — the timestamp lives inside the JSON, so it comes out as *text*.** §8.2's table
>   has three columns and not one of them is a timestamp; `ts` is a field inside `data` (§8.3).
>   `date_trunc` does not accept text, so **a cast is not optional** — and the choice of cast has a
>   wrong answer.
> - **`::timestamptz`, not `::timestamp`.** §7.1's comparison rule pins `ts` as fixed-width UTC
>   ISO-8601 ending in `Z`. Cast into **`timestamptz`** that `Z` is read and honoured. Cast into plain
>   **`timestamp`** it is parsed and then **silently discarded** (§0) — which gives the *same answer*
>   on this seed, because this seed is UTC throughout, and gives a wrong one the moment it is not. A
>   cast that is correct by luck is worse than one that is wrong, because nothing on screen
>   distinguishes them.
> - **`SET TIME ZONE 'UTC'`, on every connection the demo opens.** `date_trunc('day', …)` over a
>   `timestamptz` is asking *where does the day start*, and the **session time zone** (§0) is what
>   answers. A session left at `America/New_York` starts each day four or five hours later than one at
>   `UTC`, so the same 8,400 beats fall into **8 buckets rather than 7**, two of them partial. If the
>   SQL side simply inherits whatever the container's environment left in `TimeZone` while the Python
>   side uses something else — or the machine's local zone — **the two panes put the same row in
>   different buckets while both are computing correctly.** That is a false disagreement (§5)
>   manufactured by a setting a person at the screen cannot see, which is why the SQL pane displays it
>   (§9.3) exactly as it displays `extra_float_digits`.
>
> **The bucket's label, because both panes key their rows by it.** The bucket is rendered to text in
> the same fixed-width UTC ISO-8601 form `ts` itself uses:
>
> ```sql
> to_char( date_trunc('day', (data ->> 'ts')::timestamptz) AT TIME ZONE 'UTC',
>          'YYYY-MM-DD"T"HH24:MI:SS"Z"' )   AS "bucket"
> ```
>
> Left to themselves the two engines spell the same instant differently — Postgres's default rendering
> of a `timestamptz` is `2026-08-14 00:00:00+00`, Python's `datetime.isoformat()` is
> `2026-08-14T00:00:00+00:00` — and `bucket` is a real output column both panes key their rows by
> (§4.10's collision list forbids an alias of that name for exactly this reason). **Two spellings of
> one instant are two different keys**, and the panes would then disagree on every row of every
> bucketed pick while agreeing on every count inside them. The `AT TIME ZONE 'UTC'` is belt and braces:
> it makes the rendering independent of the session setting even if the session setting is ever wrong.
>
> **What aggregates inside a bucket** is operation 6's chosen function over §7.2 item 5's numeric read,
> accumulated in `numeric` and rounded half-up to 6 decimal places (§7.2), emitted as `AS "agg"`.
> Bucketed results are ordered by `ORDER BY bucket` (§7.4), which is a total order because
> `GROUP BY` gives one row per bucket.
>
> **The Python pane does the identical thing:** parse `ts` as an aware UTC datetime, truncate to the
> hour or the day **in UTC**, and format the label with the same fixed-width string. It must not touch
> the machine's local time zone at any step, and it must not use a naive datetime, because a naive
> datetime is the Python spelling of the `::timestamp` mistake above.
>
> **Why step 7's "exactly 7 buckets of 1,200 rows" is arithmetic and not luck.** R17 pins the span as
> seven whole UTC days and R5 pins the rate at one beat per sender per hour, so a UTC day bucket holds
> 50 senders × 24 hours = 1,200 rows and there are exactly 7 of them. Change the session time zone and
> that sentence stops being true — which is the plainest possible demonstration that the zone is part
> of the specification and not part of the environment.
>
> **What tests it: AC-43**, which runs the bucketed pick under a deliberately hostile inherited zone,
> plus **AC-9**, which now names the whole expression instead of an ellipsis.
>
> **How Evan overturns it, in one line.** *"Give me weeks and months too"* adds `week` and `month` to
> §4.4 row 7's closed set and to the label's format; nothing else changes. *"Bucket in my local
> time"* replaces `UTC` with a named zone — and the honest consequence, stated here so it is not a
> surprise later, is that step 7's clean 7 × 1,200 becomes 8 uneven buckets and the walkthrough's
> numbers regenerate.

### 7.2 Two distinctions that will otherwise cause a bug

**First: operation 6's `sum` and `avg` are not the expression functions `sum()` and `avg()`.**

- The expression functions `sum($.list)` and `avg($.list)` add up an array **inside a single record**.
  They are **outside the safe subset** and are refused by the static gate (§4.2, §4.4).
- Operation 6 reduces **many rows to one number**. That is Postgres's own `sum()` / `avg()` over
  rows, written by the demo's query builder, and it is allowed.

They share a name and are different things. The build must keep them apart, and the walkthrough
exercises both (steps 6 and 10) so that a confusion between them shows up.

**Second: exact decimal versus floating point — and why this demo cannot hand-wave it.**

A **floating-point** number (§0: `float8`) is stored in binary, so most decimal fractions have no
exact form: `0.1 + 0.2` really is `0.30000000000000004`, in Postgres and in Python alike. Two
consequences, and the second is the dangerous one:

1. **It breaks checking by eye.** A total of 8,400 whole numbers that comes back
   `41999.999999999996` instead of `42000` is not checkable on the spot — and "checkable on the spot"
   is the demo's single claim (§1).
2. **It manufactures disagreements out of nothing.** Floating-point addition is not associative:
   `(a + b) + c` can differ from `a + (b + c)` in the last digits. Postgres does not promise an order
   when it adds across rows; Python adds them in row order. So a sum, an average or a rolling average
   over floats can differ between the two panes **through no fault of either engine** — a false
   disagreement, which is the one thing that could train a reader to ignore a real one (§5).

The exact-decimal types remove problem 1 and most of problem 2. Postgres's **`numeric`** and Python's
**`decimal.Decimal`** store decimal digits rather than binary, so `0.1` is `0.1` and a sum of whole
numbers is a whole number. They are slower and unbounded in size, which is affordable here only
because Q21 kept the data small.

**They do not remove problem 2 entirely, and that is why a rule has to be pinned rather than
described.** Exact decimal does not make *division* exact: ⅓ has no finite decimal form either.
Something has to decide where to stop and how to round the last digit, and the two engines decide
differently:

- **Postgres picks a `numeric` division's result scale itself**, by its own internal rule, derived
  from the operands. There is no session setting the demo can read or set to make it produce a
  particular number of digits, so "configure Postgres to match Python" has nothing to configure.
- **Python's `decimal` has a context precision and a rounding mode the build can set**, but setting
  them to *something* gives no way of matching what Postgres just did.
- **Walkthrough step 8 is a 3-point rolling average of an integer field**: a division by 3,
  non-terminating in decimal. Under an unpinned rule that step produces the exact false disagreement
  this section exists to prevent, and its acceptance criterion is **unsatisfiable** — there is no
  pair of settings that makes the two sides agree digit for digit.

So the rule is pinned, in the same terms on both sides:

> **THE EXACT-DECIMAL RULE — the build implements this on both sides.**
>
> 1. Operations **6, 7 and 8** accumulate in `numeric` on the Postgres side and
>    `decimal.Decimal` on the Python side.
>
>    **Operation 9 is deliberately not in that list, and an earlier draft put it there.** The
>    correction is worth naming rather than quietly making, because the mistake it encodes is a
>    misreading of what the operation does: **operation 9 accumulates nothing.** It sums no column,
>    averages nothing and divides by nothing — it compares one row's value with its predecessor's and
>    keeps the row or drops it (§7.1's comparison rule). A comparison has no result scale to pin and
>    no last digit to round, so an exact-decimal rule has nothing to say to it. What operation 9 needs
>    instead is that **both panes compare the same value the same way** — pinned at §7.1, tested by
>    **AC-40** — and that its output carries a total order, pinned at §7.4. The same misreading
>    reached **AC-24(c)**, which listed the changed-rows SQL among the SQL greppable for float casts;
>    that criterion is corrected in place.
> 2. **Every division is followed immediately by a round to 6 decimal places, half-up** — ties away
>    from zero. In Postgres that is `round(x, 6)` on a `numeric`, which is documented to round half
>    away from zero (its `double precision` sibling rounds half to even — another reason operations
>    6, 7 and 8 never touch `float8`). In Python that is
>    `Decimal.quantize(Decimal("0.000001"), rounding=ROUND_HALF_UP)`, which is the same rule,
>    negatives included. **`ROUND_HALF_UP` is set explicitly** because Python's default is
>    `ROUND_HALF_EVEN` (banker's rounding), which is *not* what a person checking by hand does.
>    **Both halves are confirmed by a test rather than trusted** — AC-24(b).
> 3. **Both panes display and compare the rounded value.** Nothing compares unrounded intermediates.
> 4. No other precision setting or rounding mode is relied on anywhere, and none is read from the
>    session. The demo **sets** two session values explicitly and displays both on screen —
>    `extra_float_digits` (§4.9) and the session time zone (§7.1's time-bucket rule) — and reads
>    neither back as an input.
> 5. **How a number gets out of the JSON — "the numeric read", written once and used by operations
>    6, 7 and 8.** Every value those operations accumulate lives inside a jsonb record, so it has to
>    be lifted out and turned into a `numeric` first. There is an obvious way to do that which
>    **aborts the whole pick** on ordinary data, so the right one is pinned here rather than left to
>    each of the three:
>
>    ```sql
>    CASE WHEN jsonb_typeof( <j> ) = 'number'
>         THEN ( <j> #>> '{}' )::numeric END
>    ```
>
>    `<j>` is a scalar jsonb expression, and there are exactly two things it can be, matching §4.4
>    row 6: `data #> %(path)s` — the chosen field's path as a **bind parameter**, never SQL text — or
>    the compiled expression of a previously-defined computed column, which `compile.py` also hands
>    back as a scalar jsonb expression (`compile.py:432`). One guard wraps either.
>
>    **The wrong way, named so a build cannot arrive at it by accident.** Writing
>    `( <j> #>> '{}' )::numeric` on its own **raises** SQLSTATE `22P02` the first time one row's value
>    is a string, a boolean, a null or an object — and one raise aborts the entire statement, so a
>    single row kills a pick over 8,400 good ones. On `noun:Sample`, whose extra keys are deliberately
>    of mixed types (§8.3), that is not hypothetical. Guarding with `jsonb_typeof` turns a non-number
>    into **null** instead, and null is exactly what §7.1's window rule already tells both panes to do
>    with such a cell: it drops out of the sum *and* out of the divisor. Postgres's `sum`, `avg`,
>    `min` and `max` all ignore nulls and `count` counts non-nulls, so operation 6, and the aggregate
>    inside operation 7's buckets, inherit the rule with no special case.
>
>    **The Python pane applies the identical test**, and one detail decides whether it does: a value
>    counts only if it is an `int` or a `float` **and is not a `bool`**. Python's `bool` is a subclass
>    of `int`, so a bare `isinstance(v, (int, float))` accepts `True` and scores it as 1, while
>    `jsonb_typeof` calls it `'boolean'` and the SQL side scores it as nothing. That is a
>    one-character difference in a type check producing a real and unexplainable disagreement between
>    the panes — precisely the shape §5 says this screen must never manufacture.
>
> **Why half-up and why 6 places.** Half-up is the rounding a reader does by hand, and the demo's
> claim is that the number is checkable by hand. Six places is far more precision than the seeded
> data justifies — `payload.load` is an integer 0–100, and the only divisions are by small counts —
> and far less than the point where either engine's representation runs out, so the rule never
> changes an answer a person would care about.

A difference that survives that rule means something real.

**This does not extend to the expressions the compiler writes (operations 2 and 3).** Those stay in
`float8` exactly as `compile.py` emits them, because Q19 said reuse it as-is and because that is where
§5's defect lives — it must stay visible. Ruled at §14.1 R7.

### 7.3 Which part of a query the compiler writes

The compiler produces one expression, never a query (§4.7). The division of labour:

| Part of the work | Written by |
|---|---|
| **The static gate over the expression, before any SQL exists (§4.4)** | **the demo's own `demo/gate.py` — new code, safety-critical, in front of `compile.py` and not modifying it** |
| The computed-column expressions (op 2) | `compile.py` — reached only after the gate accepts |
| The filter's predicate (op 3) | `compile.py` — reached only after the gate accepts |
| **The two runtime probes (§4.5)** | **the demo, wrapping the compiled operand subexpressions in `jsonb_typeof(…)` and a magnitude test** |
| `SELECT`, `FROM`, the collection predicate, `GROUP BY`, `ORDER BY`, `LIMIT` | the demo's own query builder |
| The aggregate call (op 6) — `count` / `sum` / `avg` / `min` / `max` over §7.2 item 5's **numeric read** of the chosen field, in `numeric` per §7.2, emitted as `AS "agg"` | the demo's own query builder |
| The time bucket (op 7) — `date_trunc('day', (data ->> 'ts')::timestamptz)`, or `'hour'` for the other granularity, emitted as `AS "bucket"` and labelled as text — the expression, the cast, the session time zone and the label are all pinned by §7.1's **time-bucket rule** | the demo's own query builder |
| The rolling window (op 8) — `avg( <§7.2 item 5's numeric read> ) OVER (PARTITION BY (data ->> 'sender_id') ORDER BY (data ->> 'ts'), key ROWS BETWEEN 2 PRECEDING AND CURRENT ROW)`, under §7.1's **window rule**, emitted as `AS "rolling_avg"` | the demo's own query builder |
| The changed-rows flag (op 9) — `lag(data - 'ts') OVER (PARTITION BY (data ->> 'sender_id') ORDER BY (data ->> 'ts'), key) IS DISTINCT FROM (data - 'ts')`, under §7.1's **comparison rule**, emitted as `AS "changed"` | the demo's own query builder, reusing op 8's frame — §7.1's window rule fixes it for both |
| The `ORDER BY` every result carries, ending in a column no two rows can share (§7.4) | the demo's own query builder |
| **The computed-column alias check, run before any alias is emitted (§4.10)** | **the demo's own `demo/gate.py` — the same file as the static gate, the same fail-closed shape, and it runs at the same moment** |

**The four column names the builder emits are fixed here rather than left to the build**:
**`agg`**, **`bucket`**, **`rolling_avg`** and **`changed`**. Two things depend on their being fixed.
§4.10's alias collision list has to be a finite list of forbidden names, and it cannot be if the
builder picks its own; and both panes key their output columns by these same four names, so a build
that renamed one on one side only would produce a disagreement about nothing.

**No row of that table contains an ellipsis any more, and the absence is deliberate.** Three of them
did. Operation 9's `lag(…)` left the operation's *meaning* undecided, and the undecided reading was
one that filters nothing while both panes agree about it (§7.1's comparison rule). Operation 7's
`date_trunc('hour'|'day', …)` left the bucketed expression, its cast and the session time zone
undecided — three settings that can put the same row in different buckets on the two panes (§7.1's
time-bucket rule). Operation 8's `avg(…)` left both what is averaged and how that value leaves the
JSON undecided (§7.2 item 5). **An ellipsis in a specification is a decision moved to build time and
then made twice, once per pane**, and this document has already been bitten by one.

Operations 7, 8 and 9 are new code with no equivalent anywhere in GIMS, so they have no reference
implementation to be checked against — except the Python pane, which is why §5 matters for them too.
The gate and the probes are new code as well, and the thing that checks *them* is not the Python
pane: it is AC-14 and AC-17/AC-18, which test them construct by construct and row by row.

### 7.4 The ordering rule — every result the demo shows or compares carries a total order

**RULING — a ruling on delegated authority, 2026-08-21.** Authority: GA-4 (§2, §14.1). Collected as
**R12** at §14.1.

**Why this is labelled, when an earlier draft left it as a bare statement of what the demo does.**
It is substantive — it decides what "the first row" means everywhere in §10 — and it is a
**deliberate departure from GIMS**, which matters because Q23 is *"Its own app, but built GIMS's
way"*. Building it GIMS's way is the default this document was given; departing from that default is
a decision, and §14.1's promise is that every decision this document made on his behalf is labelled
as one, derived from his own words, and overturnable in a line. A departure recorded as though it
were simply a description is the one shape that promise does not survive.

**What GIMS does, and why the demo does not copy it.** GIMS's own sort
(`api/dashboard/sources.py:99-115`) builds a 3-part key giving a total order across mixed types, and
its filter matches field names tolerantly (case, spaces and underscores ignored). T-1 ruled both of
those **out** of any subset until ten separate obligations are discharged, and recorded a test that
currently fails (`measurements.json → tolerant_key_probe` returns `["T-1"]` where it should return
`["T-1","T-2","T-3"]`) — `spikes/T-1/.parts/xb-filters-sort.md` §B.1–B.2. Porting a mechanism T-1 has
an open failing test against would put a known-broken comparator underneath §5's side-by-side, where
every disagreement it produced would be indistinguishable from a real one. So Q23's "GIMS's way"
governs how the app is *built* — React, esbuild, committed bundles, FastAPI (§9.1) — and not which
comparator it borrows; the demo defines its own rule instead, narrower than GIMS's, pinned here.

**The rule, in two halves.**

> **(1) The sort, when one is picked (operation 4).** Sort on one field, by its jsonb value, **nulls
> last**, **with ties broken by the record's `key`**, and **the tiebreak always ascending**. Written
> out:
>
> ```sql
> ORDER BY ( data #> %(path)s ) DESC NULLS LAST, key ASC
> ```
>
> with `ASC` in place of `DESC` for an ascending pick — the direction is a fixed keyword from §4.4
> row 7's closed set, and the field path is a bind parameter as always.
>
> **(1a) The tiebreak's own direction, which an earlier draft never stated.** It is **`key ASC`,
> whichever way the sort field runs.** The tiebreak is not part of what the person asked for; it
> exists only to make the order total, so it must not flip when an unrelated choice flips, or the same
> two tied rows come back in opposite orders and "the first row" moves for a reason nothing on screen
> explains.
>
> **The sharper reason is that the two panes reach the tiebreak by different code and drift apart on
> it by default.** In SQL, `ORDER BY ts DESC, key` **already means `key ASC`** — `DESC` binds to the
> one expression before it, and every later component defaults to ascending. In Python the idiomatic
> spelling of the same intention is
> `sorted(rows, key=lambda r: (sort_value, key), reverse=True)`, and `reverse=True` **reverses the
> whole tuple**, so the Python pane sorts `key` *descending*. Two implementations, each idiomatic,
> each looking right, disagreeing on **every tie**. And the tie is not incidental here: **walkthrough
> step 5 is that exact pick** — sort `$.ts` descending, cap at 10 — on data where all 50 senders share
> every timestamp (§8.3), so the tie spans the whole result and the `LIMIT` boundary with it, which is
> the case `bench.py:192-194` records T-1 hitting.
>
> **So the Python pane is specified, not left to idiom:** sort ascending by `key` first, then
> **stable-sort** by the sort field in the chosen direction (Python's `sorted` and `list.sort` are
> both stable, which is what makes this work), or equivalently build a key tuple in which only the
> sort-field component is inverted. **Never `reverse=True` over a tuple that contains `key`.**
>
> **`NULLS LAST` is written explicitly for the same class of reason.** Postgres's default is NULLS
> LAST under `ASC` and **NULLS FIRST under `DESC`**, so under a descending pick the default is the
> opposite of this rule and the words have to be on the statement. The Python pane implements
> nulls-last by sorting on an `(is_missing, value)` pair — never by comparing against `None`, which
> raises in Python 3 rather than ordering.
>
> **(1b) The comparator itself, written down rather than delegated.** An earlier draft said rows whose
> sort field holds different JSON types "are ordered by Postgres's own jsonb ordering, and the Python
> pane uses the same rule". **That is not implementable as written**: it names one engine's behaviour
> and instructs the other to match without saying what it is — the same shape of hole as an ellipsis,
> and in the one place where a mismatch produces a disagreement that looks like a finding. Postgres's
> jsonb ordering is documented and finite, so it is written out here, and **both** panes implement
> this table:
>
> | what is being compared | the order |
> |---|---|
> | **different JSON types** | `Object` > `Array` > `Boolean` > `Number` > `String` > `Null` |
> | two numbers | numeric order |
> | two strings | **byte order under the `C` collation** (§0) |
> | two booleans | `true` > `false` |
> | two arrays | the longer array is greater; equal lengths compare element by element under this same table |
> | two objects | the object with more pairs is greater; equal counts compare key by key and then value by value, keys taken in Postgres's storage order — shorter keys before longer, bytewise within one length |
>
> **Two different nulls, and this data has both.** An **absent** key makes `data #> %(path)s` return
> SQL `NULL`, which is what `NULLS LAST` governs. A key that is **present and holds JSON null**
> returns `'null'::jsonb`, which is not SQL NULL at all — it is a value, and the table above puts it
> below every other jsonb value. Both occur in the seeded data: `noun:Sample` omits `due_date` from
> 5% of rows entirely (§8.3) and can hold a JSON null in a `field_n` key (`gen_data.py:43-44`). So an
> ascending sort on such a field has **three** bands, in this order: JSON nulls, then everything else
> by the table, then the absent-key rows. The Python pane has to reproduce all three, and it cannot do
> it by mapping both kinds of null to `None`.
>
> **The collation is pinned rather than inherited, and it is the half a build will get wrong.** Python
> compares strings by Unicode code point; the **`C`** collation compares bytes, and for the ASCII this
> demo's data and keys are made of, the two orders are identical. A language collation such as
> `en_US.UTF-8` is neither of those: it follows dictionary conventions and can ignore punctuation on its first
> pass, so two keys differing only in a hyphen can order differently under it than under Python. The
> demo's database is therefore created with `--locale=C` in its compose file's `POSTGRES_INITDB_ARGS`
> (§11.2), so **every** text comparison is byte order — including §7.4's `key` tiebreak, which is a
> text comparison, and including operation 9's frame ordering on `data ->> 'ts'`. A build that prefers
> to be explicit per statement may write `COLLATE "C"` on the text comparands instead; what it may not
> do is inherit whatever locale the Postgres image happened to be built with.
>
> **The walkthrough never depends on the mixed-type half**, by design: its sort step uses a
> single-typed field. The table above exists so that a pick the walkthrough does *not* make cannot
> disagree either — because §7.4's whole argument is that "the results that happen to be well-behaved"
> is not a category a person at the screen can see.
>
> **(2) Every result, sorted or not.** **Every result this demo displays or compares carries a total
> order**, and the last component of that order is a column no two rows of that result can share:
>
> | what the pick returns | the order it carries | why its last component cannot tie |
> |---|---|---|
> | rows — ops 1–5, 8, 9, with or without a sort field | `ORDER BY <the sort field, if one was picked> NULLS LAST, key ASC` — the tiebreak ascending whichever way the sort field runs, (1a) | `key` is unique **within a collection** by the table's primary key `(collection, key)` (§8.2), and operation 1 makes every pick read exactly one collection. So `key` alone breaks every remaining tie |
> | time buckets — op 7 | `ORDER BY bucket` | one output row per bucket by construction of `GROUP BY`; a bucket start cannot repeat |
> | one aggregate — op 6 | a single row | nothing to order. Stated so the rule has no hole in it rather than because it needs saying |
> | the frames inside ops 8 and 9 | `PARTITION BY (data ->> 'sender_id') ORDER BY (data ->> 'ts'), key` | §7.1's window rule, which is this same tiebreak — the two are one rule, written in two places because two operations need it |
>
> The Python pane sorts by the **identical key** with the identical comparator, and every walkthrough
> step that names a position names it under this order and no other.

**Why half (2) exists — the defect it closes.** An earlier draft pinned the tiebreak for operation 4
and for §7.1's window frames, and left every other result unordered. Meanwhile **walkthrough step 4
asserted "the first row" and step 9 asserted "the first five kept keys"**, on picks with no sort field
at all. **Postgres does not promise a row order without an `ORDER BY`.** It may return the rows of an
unordered query in whatever order the plan produced them, and that order can differ between two runs
of the identical query for reasons that have nothing to do with the data — a different plan, a
**synchronised sequential scan** joining the table mid-way (§0: a second top-to-bottom read of the
table starts wherever the first has already reached, then wraps around, so it hands back the same
rows beginning at a different place), one parallel worker finishing before another.
So those two steps could have disagreed **while both panes were entirely correct**.

That is the worst place in this document for a flake. §5 spends its whole length establishing that a
disagreement on this screen *means something*; a step that disagrees at random is the most efficient
possible way to teach a reader to skim past the real one at step 11. The rule is therefore stated over
**every** displayed and compared result rather than only the sorted ones — "results that happen to be
sorted" is not a category the person at the screen can see, so it cannot be the category a correctness
control is scoped to.

**The tiebreak is not cosmetic either.** The heartbeat data has 50 senders sharing every timestamp, so
a sort on `ts` with a cap of 10 has no defined answer without it, and the two panes would disagree at
random — the same noise, arriving by the sort instead of by the absent `ORDER BY`. T-1 hit the same
problem and solved it the same way (`spikes/T-1/proto/bench.py:192-194`: *"Postgres' sort is not
[stable], so without it a tie spanning the LIMIT boundary makes row-for-row comparison meaningless"*).

Where the two panes still cannot be made to agree, the side-by-side shows it, which is the intended
behaviour. The walkthrough's sort step uses a single-typed field so its expected answer is unambiguous.

**What tests it.** **AC-41**, plus every walkthrough step that asserts a position — 2, 4, 5, 8 and 9 —
which now states the order it asserts under.

**How Evan overturns it, in one line.** *"Sort GIMS's way"* replaces half (1) with a port of
`sources.py:99-115`'s 3-part key, and inherits T-1's open failing test on tolerant key matching along
with it. *"Don't tiebreak on `key`"* removes the tiebreak — and with it the walkthrough's ability to
name a first row at all: steps 4, 5 and 9 would have to assert unordered sets instead of sequences.
Half (2) survives both lines, because without it those steps are not testable in either version.

## 8. The data

### 8.1 It is invented, and it says so

Every record is synthetic. The seed script carries a header, and the screen carries a visible banner,
stating that the data is invented and that the heartbeat shape in particular was made up because no
heartbeat schema exists anywhere in either GIMS checkout. That labelling is Q22's own wording:
*"invented heartbeat shape, labelled as invented in the seed script"*.

### 8.2 The table

One table, mirroring GIMS's real instances table so the shape ports later
(`GUTS/spine/L1-memory/gims-ledger/migrations/pg/0001_instances.sql:13-18`, as
`spikes/T-1/proto/gen_data.py` records):

```sql
CREATE TABLE demo.records (
  collection text NOT NULL,
  key        text NOT NULL,
  data       jsonb NOT NULL,
  PRIMARY KEY (collection, key)
);
```

No other index (§4.8).

> #### THE KEY FORMAT — what `key` actually holds, and why §7.4 cannot work without it
>
> **A ruling on delegated authority, 2026-08-21.** Authority: GA-4 (§2, §14.1). Collected as **R19**
> at §14.1.
>
> **The gap this closes.** §7.4 makes `key` the last component of the total order that **every** result
> the demo displays or compares carries, and §7.1's window frames order on it as well. **No part of
> this document ever said what a `key` contains.** It is a `text` column, so it is compared as text —
> and text order is only the order anybody intends if the format is built to make it so. A build left
> to invent the format is inventing the order the walkthrough's expected answers were written against.
>
> **The wrong format is the one already sitting in this repository.** The spike's generator writes
> `f"S-{i}"` (`gen_data.py:58`), unpadded. As text that orders
> `S-0, S-1, S-10, S-100, S-1000, S-1001, S-1002, …` — row 1,000 arrives fourth. Step 2 asserts rows
> "under `ORDER BY key`", step 4 asserts "the first row" and step 9 asserts "the first five kept
> keys"; under that format all three name rows nobody could predict from the data, and to the person
> this demo is for they would read as the demo being broken. §8.3 takes `noun:Sample`'s **record** rule
> from `gen_data.py:25-45`; it does **not** take that file's key format, and this is where that is
> said.
>
> **The format: fixed width, zero-padded, ASCII, one shape per collection.**
>
> | collection | key | range |
> |---|---|---|
> | `noun:Heartbeat` | `hb-<NN>-<BBBB>` | `hb-01-0000` … `hb-50-0167` — the sender's two-digit number, then the beat's four-digit index within the span |
> | `noun:Sample` | `smp-<NNNN>` | `smp-0000` … `smp-1999` |
> | `noun:EdgeCase` | `edge-<NN>` | `edge-00` … `edge-09` |
>
> **Three properties it is chosen for, each load-bearing somewhere else in this document:**
>
> - **Fixed width and zero-padded, so text order is record order.** Every key within a collection is
>   the same length and every varying part is digits, so a bytewise comparison — §7.4 pins the `C`
>   collation — compares position by position and lands on the order a person would predict. Neither
>   pane parses a key in order to sort by it.
> - **The heartbeat key's components are `(sender, beat)`, so `ORDER BY key` reproduces
>   `(sender_id, ts)` order**, because the beat index increases with `ts` inside a sender under R5's
>   rate and R17's aligned span. That is what lets **walkthrough step 8** display one sender's rolling
>   averages in the order the window frame computed them: the frame orders on
>   `(data ->> 'sender_id'), (data ->> 'ts'), key` and the displayed result orders on `key` alone, and
>   this format makes those the same sequence. It is a property the format was chosen to give, not a
>   coincidence being leaned on.
> - **Unique within a collection** — enforced by `PRIMARY KEY (collection, key)` above, which is what
>   §7.4 needs to call `key` a total order. A seed that violated it would be refused by the database
>   rather than trusted not to.
>
> **Four digits for the beat index rather than the three that fit.** 7 days × 24 hours is 168 beats,
> so three digits would do — but R5's rate is overturnable in one line, and a rate that pushed a sender
> past 1,000 beats would silently break text ordering at that boundary under a three-digit format.
> Four carry 10,000, which is past anything Q21's row band permits.
>
> **What tests it: AC-44.**
>
> **How Evan overturns it, in one line.** *"Use the real record ids"* replaces the format with whatever
> he supplies — and §7.4's ordering then holds only if his ids are fixed-width too, which is the cost
> that line pays. *"Put the timestamp in the key"* is the other natural shape,
> `hb-01-2026-08-14T00:00:00Z`; it sorts correctly as well, costs more bytes per row, and regenerates
> every expected key in the walkthrough.

### 8.3 The three collections

**`noun:Heartbeat` — 8,400 rows.** The invented shape Q22 approved:

| Field | Content |
|---|---|
| `sender_id` | one of 50 senders, `hb-01` … `hb-50` — text, zero-padded to two digits |
| `ts` | **fixed-width UTC ISO-8601 — `YYYY-MM-DDTHH:MM:SSZ`**, the form §7.1's comparison rule requires (text order is time order) and §7.1's time-bucket rule casts to `timestamptz` |
| `status` | **exactly three values — `ok`, `warn`, `error`** — about 90% / 8% / 2% across the collection. R16 |
| `payload` | **an object with exactly two keys**: `load`, an integer 0–100 **present and numeric in every row**; and `note`, a short ASCII text from a small fixed vocabulary. Usually repeats exactly from one beat to the next. R16 |

Q22 fixes 50 senders, a 7-day span, and **about 90% byte-identical consecutive repeats**. It does not
fix the emission rate; one beat per sender per hour is this spec's choice, ruled at §14.1 R5, derived
so that 50 × 7 × 24 = **8,400** rows lands inside the small-data band Q21 requires. It does not fix
what is *inside* those four fields either, nor where the seven days sit; both are ruled below.

> #### TWO RULINGS Q22 DID NOT MAKE — the heartbeat's contents, and where its seven days sit
>
> **Rulings on delegated authority, 2026-08-21.** Authority: GA-4 (§2, §14.1). Collected as **R16**
> and **R17**. They are labelled for the reason R11 gives about the edge-case collection: §14.1's
> promise is that nothing in this document is unattributed, and Q22 named four *field names*. It did
> not say what any of them holds.
>
> **R16 — the field contents.** `status` is a **closed set of three values**, `ok` / `warn` / `error`,
> mixed about 90% / 8% / 2% over the collection. `payload` is an **object with exactly two keys**:
> `load`, an integer 0–100 **present and JSON-numeric in every single row**, and `note`, a short ASCII
> text drawn from a small fixed vocabulary. `ts` is fixed-width UTC ISO-8601.
>
> **The derivation: three mechanisms already in this document are unbuildable without those contents,
> and each fails in a way that looks like something else.**
>
> 1. **Operation 8 averages `payload.load`, and §7.1's window rule counts *non-null values in the
>    frame* as its divisor.** If `load` were sometimes absent or sometimes a string, walkthrough
>    step 8's five hand-computed numbers would be exercising the **missing-data** case and the
>    **short-window** case at once, and a reader could not tell which produced which number — while
>    step 8 exists precisely to show the short-window convention working. Present-and-numeric in every
>    row is what keeps those two apart, and it is why §7.2 item 5's numeric read never fires its
>    null branch on the headline collection.
> 2. **§4.6's ruling is defended on this data by `payload` being a container.** §8.3 already says so
>    in terms — "deliberate and load-bearing for §4.6". A `payload` pinned as an object with a fixed
>    pair of keys is what makes that argument true by construction rather than by luck of a seed.
> 3. **Walkthrough steps 3 and 4 filter on `$.status == "ok"` and `$.status != "ok"`.** Both have to
>    return a **non-empty and non-total** answer or neither step demonstrates anything. A closed set
>    of three values with `ok` dominant and the other two reliably present is the smallest shape that
>    guarantees it. The exact mix is not load-bearing; that it is a closed set with all three present
>    is.
>
> **A correction inside this ruling, because it is the same class of defect the ruling exists to
> close.** An earlier draft of §8.3's table wrote `status` as *"mostly `ok`, occasionally `warn` /
> `error`"* and a draft of this box attributed that phrase to **Q22**. It is not his. Q22's option
> text, in full, reads: *"each record carries a sender id, a timestamp, a status and a payload; about
> 90% of consecutive records are byte-identical repeats of the one before; about 50 senders over 7
> days"* (`QUESTIONS-FOR-EVAN.md:457`). **Four field names, a repeat rate, a sender count and a
> span — and not one word about what a status contains.** "Mostly ok, occasionally warn or error" was
> this document's own sentence being read back as though it were his answer, which is exactly why the
> contents needed a ruling rather than a description.
>
> **The seed's change mechanism is left to the build, bounded by two criteria rather than described
> here:** whatever it does, consecutive beats from one sender must match on `status` and `payload` in
> **88–92%** of cases (AC-8) and operation 9 must keep **700–1,100** rows (AC-40). Those two numbers
> pin the behaviour that matters; the draw that produces them does not need a spec.
>
> **How Evan overturns R16 in one line.** *"Use my real heartbeat fields"* — he supplies the shape,
> the seed is rewritten, and AC-8's band, AC-40's band and step 8's five numbers all regenerate from
> it. One consequence worth stating: if his shape carries no container-valued field, walkthrough
> step 12 moves entirely onto `noun:EdgeCase` and §8.3's argument for §4.6 rests on that collection
> alone.
>
> **R17 — where the seven days sit.** The span is the seven **whole UTC days**
> **`2026-08-14T00:00:00Z` through `2026-08-20T23:00:00Z` inclusive**, written into the seed as a
> **literal constant** and never derived from the clock. Beat *b* of every sender is at
> `2026-08-14T00:00:00Z` plus *b* hours, for *b* = 0 … 167. All 50 senders beat on the same 168
> instants.
>
> **The derivation: three things in this document break if the span floats.**
>
> 1. **§7.1's time-bucket rule promises step 7 exactly 7 buckets of 1,200 rows.** That is arithmetic
>    only if the span is whole UTC days. A span beginning at 09:00 gives **8** day buckets, two of them
>    partial, and step 7 could not state a number at all.
> 2. **§8.4 promises that two seed runs on two clean checkouts produce byte-identical rows.** A span
>    anchored on `now()` at seed time produces different rows tomorrow, so `demo/expected-answers.json`
>    and the whole walkthrough would rot overnight while every test still passed on the day it was
>    written. A literal constant is the only anchor that keeps §8.4's promise.
> 3. **R19's key format numbers each beat *within the span*.** A key is only well-defined if the span
>    has a fixed first instant.
>
> **A fourth consequence, stated because §7.4 leans on it:** all 50 senders sharing every one of the
> 168 instants is what makes §7.4's `key` tiebreak necessary rather than decorative — a sort on `$.ts`
> has 50 rows tied at every value, and walkthrough step 5's cap of 10 falls inside one of those ties.
>
> **How Evan overturns R17 in one line.** *"Make the data land on the current week"* — the seed
> computes an anchor **once**, and that anchor is committed rather than recomputed at each run, or
> §8.4's determinism goes with it. The seven days must stay aligned to UTC midnight either way, or
> step 7's 7 × 1,200 stops being true and its acceptance criterion (AC-9) has to be rewritten.

So bucketing by day gives exactly **7 buckets of 1,200 rows** (50 senders × 24 hours), and the
walkthrough's expected numbers are arithmetic rather than a lucky draw.

Byte-identical means it: consecutive records from one sender carry an identical `status` and an
identical `payload` — the same `load`, the same `note` — and differ only in `ts`, roughly 9 times in
10. Roughly one beat in ten changes something, which is what gives `payload.load` enough movement for
a rolling average to be worth looking at, and what gives operation 9 roughly 900 rows to keep out of
8,400, while keeping the repeat rate Q22 fixed.

Note that `payload` is an **object**. That is deliberate and load-bearing for §4.6: the demo's
headline collection genuinely carries container-valued keys, so a rule that refused `==` on any field
reference would be refusing over a real possibility, not an imaginary one.

**`noun:Sample` — 2,000 rows.** GIMS-shaped arbitrary-key records, following the **record** rule
already implemented in `spikes/T-1/proto/gen_data.py:25-45`: `id`, `status`, `due_date` (5% of rows
omit it entirely), `priority`, plus 5–15 extra keys of mixed types per row, named `field_0` …
`field_14` — one of those types being an object, `{"code": …, "n": …}` (`gen_data.py:46`), and another
being JSON null (`gen_data.py:43-44`). This is what makes the demo's data look like GIMS data rather
than like a tidy example, and it is why §7.4's comparator has to handle mixed types and two kinds of
null. **Its key format is *not* taken from that file** — `gen_data.py:58`'s unpadded `S-{i}` does not
sort as text; §8.2's R19 replaces it.

> #### RULING — `noun:Sample`'s size is this spec's, not his
>
> **A ruling on delegated authority, 2026-08-21.** Authority: GA-4 (§2, §14.1). Collected as **R18**
> at §14.1. Labelled for the same reason as R11 and R16: **Q22 fixed nothing whatever about this

> settled, so it is settled here.
>
> **The derivation, from Q21.** His band is *"5,000 to 20,000 rows, small enough that you can read it
> and check by hand"*. The heartbeat's 8,400 (R5) and the edge cases' 10 (R11) leave headroom inside
> it, and this collection's job — stated above, to make the demo's data look like GIMS data rather
> than a tidy example — is served by a couple of thousand rows of 5–15 mixed extra keys apiece. Fewer
> and the mixed-key shape stops showing up reliably in any pick a person makes; many more and the
> headroom under GIMS's 20,000-row `MAX_SCAN` disappears, which would put the truncation Q21
> explicitly declined back on the screen (§6). **10,410 in total** sits inside his band and below that
> cap.
>
> **How Evan overturns it, in one line.** Any other count — AC-7's number and the 10,410 total
> regenerate with it, and the only thing that has to survive is Q21's band and the 20,000 ceiling.

**`noun:EdgeCase` — 10 rows, labelled, one purpose each.** A small, explicitly-labelled collection

demonstrated on purpose rather than waited for.

| what it holds | what it is for |
|---|---|
| `{"a": 1e300}` | §5's seven "value → null" divergences — inside the 12-decade band the shipped 297-digit guard gets wrong |

Two notes the build needs. The `1e400` row is written by the seed as **raw JSON text**, not through a

anyway, and `jsonb_typeof` calls it a `number` (measured, `EXPERIMENTS.md` §1.2). And because §4.5's

refusal for picks that never read `$.huge` — which is what keeps step 11 working on the same
collection.

### 8.4 Determinism

The seed runs from a fixed random seed. Two runs on two clean checkouts produce byte-identical rows.
Without that the walkthrough's expected numbers cannot be written down at all.

### 8.5 What the seed publishes

After loading, the seed writes `demo/expected-answers.json`: for each walkthrough step, the pick and
the value it should return. This is the machine-readable half of the do-this-expect-that walkthrough
the ticket's MUST INCLUDE 4 asks for, and it is what makes the acceptance criteria runnable by
someone who is not Evan.

**It is not a substitute for the side-by-side, and this spec is explicit about the distinction.**
Q24 offered three options: expected answers written down (option 1), both answers on screen
(option 2), and both of those (option 3). **Evan ticked option 2.** The file specified here exists
to make §12's criteria testable and to fill in the walkthrough document's numbers — not as a second
checking route in place of the screen. If he considers it outside what he approved, deleting it costs
one line and the walkthrough carries its numbers inline instead (§14.2 item 1). The side-by-side is
not droppable either way (§5).

## 9. The application

### 9.1 Built GIMS's way (Q23)

Q23: *"Its own app, but built GIMS's way"* — its own app in this repo, so the same code drops into
GIMS later without a rewrite. Read from GIMS's own build file (`GIMS-Project/build.mjs:1-9`):

- **React 18**, pages as `.jsx`;
- **esbuild** producing a shared `vendor.js` plus one bundle per page;
- **bundles committed to the repo** — the header says it plainly: *"committed; FastAPI serves them,
  no node at serve time"*;
- a **small FastAPI server** serving the bundles and a thin JSON API, on `127.0.0.1:8787` (§11.1);
- **no Node needed to run the demo**, only to rebuild the front end.

### 9.2 Layout of the screen

Three regions:

1. **The picking controls** — the nine operations of §7.1.
2. **The SQL pane** — the generated SQL, in full.
3. **The two result panes, side by side** — SQL answer and Python answer.

The design stage (§13) decides how this looks. This spec fixes only what must be present.

### 9.3 The SQL pane

- Shows the SQL for the current pick, formatted to be read.
- Shows it with its bind parameters substituted in, so it reads as a real query. The compiler already
  has this helper — `render_for_display` (`compile.py:450`), whose own comment (`:445-449`) reads
  *"NEVER execute this -- the harness always executes the parameterised form."*
- **What actually runs is the parameterised form**, with every value and every field name passed
  separately. This is not decoration: the compiler already binds JSON field names as parameters
  (`compile.py:222-240`, `_t_field` → `self._bind(key, 'text')`), which is exactly what Q11's ticked
  option requires — *"The compiler never writes field names into SQL text"*. Reusing it as-is
  preserves that property; a rewrite could lose it silently.
- **Shows the computed-column alias exactly as it was emitted** — `AS "alive"`, double-quoted — which
  is the one piece of user-typed text in the statement that is not a bind parameter. §4.10 rules what
  is allowed there and AC-38 tests it with hostile input; the pane is where a reader can see that the
  rule was applied.
- Shows the two runtime probes (§4.5) as well as the pick's own query, so the extra questions the
  demo asks the database are visible rather than hidden.
- States the two session values the query ran at — `extra_float_digits` (§4.9) and the session time
  zone (§7.1's time-bucket rule). Both change the answer, and neither is visible anywhere else on
  the screen.
- **When the pick is refused, this pane says which layer refused it and why.** For a layer-1 refusal
  there is no SQL to show, and the pane says exactly that: the expression was refused before any SQL
  existed, and names the construct. For a layer-2 refusal the pane shows the probe that fired, the
  condition it found, and the fact that the pick was abandoned before its own query ran.

### 9.4 Anyone can re-slice (Q25)

Q25: *"Any viewer can re-slice live"* — there is no author/viewer split, no permission gate, and no
saved-view concept. Every visitor gets the full controls, the SQL pane is in front of everyone, and
each pick fires a fresh query. This differs from GIMS today, which splits `/dashboard` from
`/dashboard_admin`; the difference is his decision, not an oversight.

### 9.5 The Python pane's calculator

Q24 requires *"a second, in-memory calculator that works out the same pick the way GIMS does today"*.
The ticket forbids depending on either GIMS checkout being present. Both can be satisfied only one
way, so this spec rules it (§14.1 R4):

> The demo vendors a **byte-identical copy** of `GIMS-Project/core/dashboard/expr.py` into
> `demo/vendor/expr.py`, together with its sha256 recorded in a committed manifest, and a test that
> re-checks the copy against the GIMS tree **when that tree happens to be present** and skips
> when it is not.

Three reasons this is the right copy to take: it is 646 lines and imports nothing outside the Python
standard library; it is the same file the T-1 investigation used as its reference; and it supplies
both halves of what the demo needs — the parser that feeds the gate and the compiler their AST, and
the evaluator that computes the Python pane. Its sha256 today is
`90cbb56d04b08b825ef38dbd1b805ad2b877a0f5e5154e2dc38d9944f4ad4c49` (verified by `sha256sum`).

Around it the demo writes its own row-level runner — filter, sort, cap, aggregate, bucket, window,
changed-rows-only in Python — because GIMS has no equivalent for buckets, windows or change
detection to copy. Its arithmetic follows §7.2's exact-decimal rule.

**Where its input comes from matters more than anything else in this section.** The Python pane reads
the **source rows** — the whole collection, before any filter, sort, cap, aggregate, bucket or window
— out of the same database, and then applies the pick itself, in Python, from scratch. It must not be
handed the SQL query's result, or it would be checking the SQL against itself and would agree with
every wrong answer. It must not rebuild the data from the seed script's memory either, or the two
panes are describing different worlds and an agreement proves nothing. Reading a whole collection is
affordable precisely because Q21 kept the database small.

### 9.6 The SQL runtime the compiler needs

The compiler's output calls 21 helper functions in a Postgres schema named `xpr`, defined in
`spikes/T-1/proto/runtime.sql` (verified: 21 `CREATE OR REPLACE FUNCTION` statements in 427 lines).
The seed installs that file into the demo database **unmodified** — including the 297-digit guard of
§5. No `xpr` function may appear in an index (§4.8). The demo's own probes (§4.5) live in the demo's
own schema and never touch `xpr`.

and no code change.

**What happens when a tree is absent: the checks skip *loudly*.** A silent skip is worse than a
failure, because a run that quietly did less than it claimed reads exactly like a clean one. "Loudly"
means all four of these, and a build that does only the first three has not met it:

1. The check reports **`SKIPPED`** — never `PASSED`, and never nothing at all.
2. The skip line **names the path it looked for**, e.g.
   `SKIPPED AC-34 (tree half): no GIMS checkout at /home/corgea/Desktop/Coding Projects/GIMS-Project`

3. `./run-demo test`'s **final summary line counts skips separately** — `… 3 skipped (GIMS checkout

4. **Everything that does not need the tree still runs and still has to pass.** AC-34 splits in two:

**`./run-demo up` never depends on either tree, in any circumstance.** A missing GIMS checkout cannot
stop the demo launching, seeding, answering a pick or showing both panes. It can only stop the demo
re-checking itself against GIMS. AC-39 tests exactly that.
