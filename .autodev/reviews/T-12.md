## Findings, by severity

### BLOCKING

**B1 — "Running the demo" overstates the offline/portability claim (README.md lines 54, 68-70).**
As written: "You need Docker and `python3`... Python dependencies are installed offline from a
committed wheelhouse (`--no-index`), so `up` and `test` both work with the network switched off and
with Node removed from `PATH`." Two things make this not true as stated:
1. `demo/vendor/wheels/README.md` line 4: the committed wheelhouse is built "for CPython 3.12 on
   manylinux x86-64" only; `psycopg-binary`/`pydantic-core` are `cp312-cp312-manylinux2014_x86_64`
   wheels. `pip install --no-index` on macOS, native Windows, or non-x86-64 Linux has no matching
   wheel and — because `--no-index` forbids any PyPI fallback — fails outright, regardless of network.
2. The acceptance criterion this claim is presumably drawn from, AC-32 (`.autodev/specs/T-2.md`),
   is narrower than the README implies: "no network access beyond pulling the Postgres image." First
   run of `./start.sh`/`./run-demo up` needs network to pull `postgres:16-alpine` unless it's already
   cached locally.
   **Fix:** in the "Running the demo" paragraph, replace the blanket claim with something like:
   "Tested on Linux x86-64 with Python 3.12 — the committed wheelhouse is built for exactly that
   combination, so other platforms/Python versions may need network access for `pip` to resolve
   dependencies. Docker still needs network once, to pull the `postgres:16-alpine` image, unless it's
   already cached." This is a wording fix only — no code changes needed, and it costs the README two
   sentences.

### New finding — B2: the compiler/runtime pytest command doesn't match either README (BLOCKING)

Lines 80-83: "`./run-demo test` runs the demo's own suite (`demo/tests/`). The compiler and runtime
suites are plain pytest, run with the interpreter `up` created:
`demo/.venv/bin/python -m pytest compiler/tests runtime/tests -q` (`compiler/README.md`,
`runtime/README.md`)."

Checked against what those two files actually document:

- **`compiler/README.md`**'s command is `./run-demo up` **then**
  `AUTOSQL_COMPILER_DSN="host=127.0.0.1 port=55440 user=autosql_demo password=autosql_demo_password
  dbname=autosql_demo" demo/.venv/bin/python -m pytest compiler/tests -q` — i.e. it needs the DSN
  env var pointed at the demo's own database, not just the venv `up` built. `compiler/tests/test_compiler.py`
  confirms: `needs_db = pytest.mark.skipif(not DSN, reason="set AUTOSQL_COMPILER_DSN to the demo's
  Postgres")`, gating 3 of the file's 8 top-level tests.
- **`runtime/README.md`**'s command is a **separate throwaway Postgres container** — `docker run
  ... -p 55434:5432 pgvector/pgvector:pg16`, then loading `runtime/runtime.sql` into it by hand
  (`docker exec -i ... psql ... < runtime/runtime.sql`), then
  `AUTOSQL_RUNTIME_DSN="host=127.0.0.1 port=55434 ..." demo/.venv/bin/python -m pytest runtime/tests -q`.
  This container is **not** the one `./run-demo up` creates (that one is port 55440, seeded with
  demo data, not `runtime.sql` loaded standalone). `runtime/tests/test_runtime.py` gates 12 of its
  18 top-level tests behind `needs_db` (`skipif(not DSN, reason="set AUTOSQL_RUNTIME_DSN to a
  throwaway Postgres")`).

The new README sentence mentions neither DSN and, for `runtime/tests`, omits the separate container
and manual schema load entirely — it reads as though the single interpreter `up` already created is
enough to run both suites as documented. It is not: run exactly the command the README now gives,
with no other setup, and pytest will **silently skip** roughly a third of `compiler/tests` and
**two-thirds of `runtime/tests`** (the ones behind `needs_db`) rather than run them — producing a
