> **Vocabulary, because this document uses shop jargon.** A **stage** is one step of work on a
> ticket. A **gate** is a checkpoint a ticket cannot pass until a named person signs it. A **block**
> is a deliberate stop recorded on the ticket with a reason and a remedy — *this ticket has one*. A
> **receipt** is the evidence a stage recorded when it finished. A **go-ahead (GA-*n*)** is a
> recorded line from Evan authorising a class of decisions, logged verbatim with a timestamp in
> `.autodev/events.jsonl`. A **ruling on delegated authority** is a decision a session took *for*

## The risky part, first — four punch-list items describe SQL that will not run as the spec implies

`.autodev/specs/T-2-punchlist.md` carries sixteen items the sixth spec review found and deliberately
did **not** refuse the spec over. **Items 2, 3, 4 and 5 are the ones to read before writing any
code.** The punch list flags them itself, in its own header: they were judged non-blocking because
the spec's own acceptance criteria would catch them *during* the build — not because they are
harmless. Three of the four make Postgres raise; the fourth runs and produces output nobody should
trust. Read them in the punch list, not from this summary — the summary is here so nobody starts the
build without knowing they exist.

| # | what the spec implies | what Postgres actually does |
|---|---|---|
| **2** | §4.4 row 6 says a previously-defined alias reaches "the aggregate as SQL text" | **Raises.** Postgres will not resolve a SELECT-list alias inside an aggregate in the same SELECT — `SELECT expr AS busy, sum(busy)` fails. §7.2 item 5 already pins the runnable form (re-emit the compiled expression); row 6 has to say that. `ORDER BY` and `GROUP BY` alias references are fine as written. |
| **3** | Operation 9 ("show only rows that changed") is described as a **filter** and emitted as a flag column `AS "changed"` | **Raises.** A window function cannot appear in `WHERE`, so the filtering pass needs a subquery or CTE wrapped around the flag. The spec never says so, and AC-40(a) counts kept rows as though it does. |
| **4** | Operations 7, 8 and 9 hard-code the field names `ts` and `sender_id` | **Runs, and is meaningless.** Those fields exist only on `noun:Heartbeat`. On `noun:Sample` and `noun:EdgeCase` the operations degrade to one partition, one NULL bucket and a whole-record comparison — identically on both panes, so **no wrong number**, but meaningless output from a control the reader is being taught to trust. AC-25 asserts only reachability. Either restrict those three operations to the heartbeat or define a per-collection ordering and partition key. |
| **5** | any combination of operations is pickable | **Raises.** Nothing pins which combinations are legal: operation 7's `GROUP BY` alongside an ungrouped computed column or an ungrouped sort field raises. The UI has to disable the illegal combinations, or the spec has to name them. |

**A fifth item is adjacent and equally cheap to hit:** punch-list item **1** — §7.1's time-bucket
rule prints two code fences that both end `AS "bucket"`, and a build that emits both gets
`ORDER BY "bucket" is ambiguous`. Only one column is emitted; §7.3 and AC-43(c) settle it as the text
label.

**Items 4, 5 and 6 are also the three that are visible product choices rather than implementation
detail** — which operations the screen even offers per collection, which control combinations get
greyed out, and one displayed session setting (`extra_float_digits = 1`) whose correctness T-3 is
still testing. They are named as such in the wrap-up form (item 26) in case Evan wants to rule them
himself.

## The block, and exactly what clears it

**Why it exists.** Evan's Q27 answer was *"Add a design stage and a look sign-off"* — he approves how
the screen looks **before** anyone codes it, rather than first seeing it at the final acceptance gate.
The `design` modifier gave T-2 a design **stage**, and that stage ran and produced the mock. But this
shop's checkpoint list (`.autodev/data/gates-policy.json`) defines seven gates — `spec_ready`,
`merge`, `accept`, `deploy`, `sp_decide`, `ex_decide`, `compliance` — and **none of them is
`design`**. So there was no checkpoint for the look sign-off to happen at, and the ticket flowed
straight through to `queue`. It got there under **GA-5** (*"I'm about to be AFK for a long time. Be as
autonomous as possible…"*), which is an AFK note, **not** approval of the screen. A block was put
where the missing gate should have been, so that the next session told to keep going does not build a
UI Evan has never seen.

**What clears it,** verbatim from the ticket's own `blocked.remedy` field:

> Evan looks at the artifact and says go, or says what to change. Then: `tracker.mjs unblock T-2 --by <actor>`

That is the whole of it. He looks at
`https://claude.ai/code/artifact/334be0e8-4bda-4893-909f-293fd6b74e47` (or opens
`design/t2-demo-mock.html` locally), and either approves it as drawn, approves it with changes, or
answers the five questions in `design/t2-demo.md` part 9 — **should agreement announce itself as
loudly as disagreement · side-by-side or stacked on his monitor · how much SQL at rest · how
insistently the invented data says it is invented · is the picking column too long.** Ten minutes
driving the mock answers all five. Then the ticket is unblocked and moves to `locate`.

**Do not clear this block without him.** It is not a process artefact to tidy away; it is standing in
for a checkpoint he asked for and the pipeline could not provide. If he would rather make it a real
checkpoint, note the trap already found in the tool: adding `"design"` to
`.autodev/data/gates-policy.json` **alone does nothing** — `tracker.mjs` silently skips a policy entry
for a gate that is not also defined (`if (!g) continue`). Both files have to change, and `tracker.mjs`
is off-limits to sessions in this repo.
