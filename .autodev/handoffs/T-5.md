## What was found

1. **The stored data is clean, and the finding is solid.** 8 SQLite stores, `mode=ro&immutable=1`,
   38,457 rows / 1,141,929 strings: **0 non-ASCII digits, 0 non-ASCII whitespace.** Reproduces
   T-1 §D.4 with a fresh instrument 11 days later — **four instruments now agree** — and the
   tolerance control passes (48,297 strings carry *other* non-ASCII), so the zero is load-bearing.
2. **The published denominator overstated it ~7,600×.** "0 of 1,096,202" counts every string and
   object key, most of which can never coerce. The decision-relevant base — strings a dashboard
   would actually turn into a number — is **144**, of which **137** are in the one tenant project.
3. **The door is open.** `csv.DictReader` yields every cell as text verbatim; `_clean` maps only
   `"" → None`; and the gate meant to enforce *"this field is a number"*
   (`GIMS-Project/core/words/validation.py:88-97`) is **bare `float(str(value))`**, which accepts
   all 670 non-ASCII `Nd` digits. Driven against the real GIMS validator: **8 of 10 forms admitted**,
   including a `7` wrapped in non-breaking spaces (an ordinary Excel artifact). They land in
   **required** fields — `Sample Weight (g)` / `Dilution Weight (g)` on `Potency Sample` and
   `Terpene Sample` — and **all 6 number-declared fields that carry rows hold strings, none holds a
   JSON number**, so this is how every number in the project is read.

## Also found, out of charter, reported not pursued

`Glove.size` is declared `type: float` and contains `'lmao im a changling'`. `is_number()` rejects

plans to build per-type expression indexes on trust.
